# 监控与通知

「系统设置 → 监控与通知」由超级管理员管理渠道、规则、投递记录和代充接管。管理员可在「监控中心」查看及确认告警。确认记录当前处置状态，恢复以监测依据为准。通知内容使用固定模板，仅包含事件编号、时间、脱敏任务尾号、适用计数和后台入口。

设置与告警历史复用现有加密文档和版本检查。配置变更、测试、接管、登记已核实事件及人工确认写入操作记录。Telegram 测试先进入队列，取得匹配目标聊天的消息编号才显示已接收。单次发送结果不明时进入待核对。明确限流按 Telegram 的等待时间重试，最多尝试三次。更换 Bot 或接收编号会使受影响渠道的测试回执失效，旧目标的待发项将取消。

## 首版观测与接收方

| 规则 | 初始条件 | 接收方 |
| --- | --- | --- |
| 全站／核心不可用 | 独立探针每分钟核对 HTTPS 和就绪响应，连续三次失败开报、连续两次成功恢复 | 站外探针指定的运维接收人 |
| 探针失联、证书临期 | 已配置签名的探针四分钟未回传；证书剩余天数小于或等于十四天 | 运维接收人 |
| API、磁盘、代充执行器 | 十分钟内至少 50 个计入样本的响应，至少五次 5xx 且错误率达到 5%；业务盘可用空间低于 15%；执行器就绪连续三次失败 | 运维接收人 |
| 登录与权限 | 五分钟内同一账号五次失败或限流，或十二次限流；员工访问权限或凭据变更；十分钟内同一员工二十次指定敏感资料读取；通知设置变更 | 安全管理员 |
| 代充异常 | 锁定原版任务回执中的明确付款待核实；运行三十分钟仍未结束；十五分钟内五笔明确失败；入口返回确切线路或卡池拒绝 | 代充管理员。接管后的卡池通知沿用代充接收范围 |
| 后台任务 | 订单同步、汇率采集及后台同步连续失败；邮箱查询十分钟内三次服务端错误；云备份完整性错误或已有工作进程回执持续失联 | 运维接收人 |
| 已核实的安全／重复扣款 | 超级管理员核对内部证据后用其 UUID 登记，同一证据在保留窗口内去重 | 安全管理员 |
| 代充成功、单笔明确失败和日报 | 已接管订阅沿用旧开关。日报默认关闭，按北京时间前一日的可完整核对的原版自助任务批次汇总 | 代充接收人或运维接收人 |

登录账号分组使用进程内临时摘要。接口指标基于当前应用进程完成的请求，低样本及尚未收到有效回执的来源显示未知。云端上传校验和表格写后核对分别记录，闲置的工作进程以心跳反映可达性。配置尚未验证的接收人无自动投递。

备份及表格回执预留为独立配置。启用时给两个工作进程提供专用的可写回执挂载，给主站提供同一目录的只读挂载，并分别设置对应容器内的绝对路径 `ID_MONITOR_WORKER_RECEIPTS_DIR`。目录由工作进程账号持有，权限为 `0700`，文件仅供相同服务身份读取。业务数据库挂载继续沿用只读权限。未配置回执目录时，这两项检查显示未启用。

代充执行状态通过既有原版管理读取接口核对，代充入口的拒绝信号来自明确的原版响应。已提交后结果待核实的任务须查原单回执。当前付款资料缺少把两个独立实扣回执唯一关联到同一任务的机器证据，重复扣款采用人工核实入口。原版管理任务列表覆盖自助代充近期 200 条。浏览器本地执行、独立商店任务、截断批次及其他无可信回执的来源需另行接入才能完整统计。

## 首次配置及代充接管

1. 用超级管理员在系统设置保存 Bot 和数字接收编号。按用途分别配置安全管理员、运维接收人、代充管理员和代充群组。测试消息由管理员逐个主动确认发送，在投递记录核对 Telegram 的接收回执。
2. 在代充仍由原版发送时选择「导入原代充订阅」。系统读取实际开关和目标。原版只返回已遮挡的 Bot 密钥，统一渠道用管理员已授权的密钥独立配置。新安全和运行规则先检查接收范围，再启用自动发送。
3. 在既有维护窗口停收新任务，确认原版维护状态、运行中的任务数和账单待核对范围。选择「接管代充业务通知」。系统先记录接管状态，再关闭原版成功、失败和卡池三个业务开关，回读关闭结果后才由统一渠道处理切换后的任务。原版验证码所用的 Bot、管理员编号和路由参数保留原值。
4. 关闭操作结果待核对时使用「继续核对接管」。已读回关闭的情况下直接完成接管。恢复接单前核对统一接管状态、旧入口指引和目标回执。需要退回旧发送器时先停用统一发送、确认待发队列并沿既有变更流程核对原订阅恢复范围。

## 独立探针

正式应用提供同域 HTTPS 的 `GET /health/ready`，只有现有认证资料、会话目录和业务存储可读取时返回就绪标记。它只给出就绪状态。站外探针在与站点独立的主机和故障域运行 `node server/monitoring-site-probe.mjs`。为进程提供专用的绝对状态目录，权限为 `0700`，由服务管理器保证单实例并持久保留状态。状态文件仅保留检测和告警证据。

站点与探针共享受管的 `ID_MONITOR_PROBE_SECRET`。域名、运维 Bot、接收编号和状态目录四项配置只交给探针进程。站点恢复后，探针通过签名回传故障及恢复时间和开报接收状态，站内按同一事件编号归档。探针直接发送整站 P0 消息，站内记录避免重复投递。正式验收应从站外核对域名和就绪语义，并以模拟故障检查连续阈值、恢复和回传，再按接收方授权验证 Telegram 实收。

## 验证入口

- `node --test test/system-monitoring.test.mjs` 使用内存文档和合成 Telegram 回执。
- `node --test test/system-monitoring.browser.mjs` 在浏览器拦截业务请求，核对桌面、手机、深浅主题、分页、草稿、读写失败、配置权限和确认流程。
- 数据库持久化、外部探针运行、真实接收人验证和生产接管使用隔离验收及正式发布记录分别登记。
