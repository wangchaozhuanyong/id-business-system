按用户要求只处理性能，不调整布局、不增删业务功能。改动集中在 3 个实现文件，没有修改 CSS、HTML、接口契约、数据库结构、权限、付款执行步骤或构建依赖。原有工作区修改及上一轮实时／并发修复均保留。

检查覆盖：54 个导航页面、客户／订单／库存搜索、1,000 与 10,000 条合成资料、4 倍 CPU 限速、重复切页内存与接口读取、服务端账号摘要与保存前关联校验。浏览器使用静态资源拦截及合成接口；没有启动本机网站、Docker 或数据库，没有写入真实业务。

这些结果证明本地代码中的性能瓶颈及修复效果，不能替代真实服务器、数据库负载、网络延迟和外部充值／邮箱服务的线上测量。

## 定位到的原因与实施方案

| 具体原因 | 修复方式 | 保留的行为 |
| --- | --- | --- |
| 每笔订单按邮箱扫描全部库存；侧栏续费数量也调用该路径，因此多个页面一起变慢 | 按库存快照建立账号类型／身份索引，重复查询复用索引 | 重复身份仍返回歧义结果，收到新快照或本地变更时重建 |
| 邮箱搜索为每一条邮箱重新扫描账号和注册记录 | 建立账号编号、库存邮箱、成功注册记录索引 | 仍按原注册平台、客户自有／库存及重复账号规则判断 |
| 每个客户都扫描全部订单；租户每一行重算全部订阅 | 当前渲染内按客户分组订单，复用服务摘要；租户关联数一次汇总 | 搜索范围、次数、排序、分页及历史开通条件不变 |
| 订单搜索反复扫描客户名单；已知客户的订单仍做联系方式推断准备 | 客户／租户按编号查找；仅遇到未明确关联的订单时构建联系方式匹配表 | 明确编号、联系方式推断、匿名订单和冲突判定规则保留 |
| 服务端每个账号重新扫描全部订单和客户 | 单次批量读取内建立目标索引，候选记录仍交给原规则核验 | 平台编号、个人订阅目标、释放记录、KYC、重复编号取首条等行为保留；不跨请求缓存 |
| 保存前逐笔旧订单扫描全部账号 | 同次校验按账号编号查找 | 原账号、客户关联不可被普通更正替换的限制继续执行 |

没有把刷新、搜索、校验或业务记录移除来换取速度，也没有引入固定频率刷新。

## 本机对比测量

下表前后均使用相同的 10,000 条合成资料。浏览器数字是同步渲染／输入处理耗时，不含人为等待；不是线上 INP 或接口总耗时。服务端数字是纯函数连续 3 次测量的中位数，不包含数据库 I/O、加解密和网络。

| 场景 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 客户列表渲染 | 4,971 ms | 55 ms |
| 租户列表渲染 | 7,578 ms | 53 ms |
| GPT 订单列表渲染 | 4,297 ms | 70 ms |
| 续费页面渲染 | 6,328 ms | 44 ms |
| 客户搜索输入处理 | 4,783 ms | 47 ms |
| 邮箱搜索输入处理 | 4,656 ms | 35 ms |
| 订单搜索输入处理 | 4,361 ms | 30 ms |
| 服务端批量账号摘要 | 3,660 ms | 15 ms |
| 保存前账号关联校验 | 165 ms | 2.4 ms |

4 倍 CPU 限速、10,000 条资料下，三项搜索输入处理为约 99–183 ms；所测页面同步构建约 103–346 ms。包含完整客户选择项的录单页仍较重，不能据此承诺所有设备、全部数据规模都无长任务。

连续切换 80 次：垃圾回收后的 DOM 节点保持 2,666、事件监听保持 110；第 12 次至第 80 次基础接口请求总数保持 4，JS 堆约从 2.99 MB 到 3.17 MB。本次有限循环没有发现随切页次数持续累积的 DOM、监听或重复读取。

测量使用 Chromium CPU 采样、长任务观察和独立的 Node 计时。超过 50 ms 的主线程任务会阻塞后续交互，因此先消除反复扫描，再检查渲染和内存；这与 Chrome 的性能分析方法一致。[长任务说明](https://web.dev/articles/optimize-long-tasks)、[Chrome 性能分析参考](https://developer.chrome.com/docs/devtools/performance/reference)。
