# 未使用充值码归还

用户在最小核心例外方案后，于 2026-11-08 明确要求完成剩余工作并提交、推送、合并 main、正式部署与线上验证。此文描述实现与发布门禁；最终结果以本轮发布回执为准。

## 业务行为

申请记录保留原申请数量和“已发码”审核状态，另显示可归还、未用／使用中／已用／待核对、已归还及归还待核对数量。我的充值码使用稳定领用编号，支持逐项和所选项目核对，增加已归还和归还记录页签、搜索及套餐筛选。普通领码人只处理自己的码，沿用现有登录和角色边界，没有新增员工模块权限。

确认前完整核对本次选择，任一项目变为不可归还就返回新核对列表，要求重新确认。确认后的逐项竞争可能导致部分完成，结果必须逐项展示。未知状态、已交付、历史尝试、冷却、人工待核对付款均阻止归还，不能因失败任务的码显示 unused 就推定未付款。

## 原子失效与恢复

- 新增原生服务内部接口 `/api/admin/cdks/returns/{check,commit,receipt}`，均为 POST。外围适配器只接受已有受管身份 `order-reconciliation`，不会向浏览器暴露原生令牌。外层用户接口沿用 `/api/local/recharge-codes`，增加 `return-preview`、`return`、`return-reconcile` 动作。
- 原版 `mysql-store.js` 只导出既有 `withTransaction`；`server.js` 只增加内部接口接入。所有原有数据库、验码、`markCdkUsed`、付款、换卡和重试函数保持原内容。
- 失效在同一 InnoDB 事务中锁定原码，核对未使用、未交付、正常可用、无尝试／任务／付款待核对；置 `is_active=0` 并写入幂等回执。与原版 `markCdkUsed` 对同一行的条件更新互斥，最多一方成功。
- 回执表 `id_recharge_code_returns` 以原码唯一、操作编号为主键，外键禁止删除已归还原码。原生导入本身不覆盖重复码，因此已归还码不能删除后原样重新发放。
- 外层在现有加密 `recharge-codes` 文档的原申请上保存 `returns[]` 意图和状态。先记 pending，再调用原生接口；超时先回读原操作，落账失败或重启时用相同操作号核对并继续。异步旧回执不能把 returned 降级。原申请响应和列表立即隐藏 pending／returned 的完整原码，复制入口也同步限制。
- 原请求和原码的员工归属依据保留，订单同步不改历史归属。归还不会取消任务、退款、释放银行卡、改变订阅、重发新码或通知他人。

## 迁移与核验

新增迁移 `modules/recharge/codexdaichong/code-returns-migration.sql` 只创建一张附属表，不修改既有字段或历史数据。生产入口 `deploy/recharge-core/entry.mjs migrate-native-code-returns` 沿用原有私有 stdin、确定镜像、数据库身份检查；隔离金丝雀使用 `migrate-canary-code-returns`。迁移可幂等执行。

原版 200 个文件继续全量核验，196 个保持原内容；4 个经两份精确清单串联批准。原有 `routing/` 清单保持独立，`returns/manifest.json` 校验以选路后 server.js 为基准的独立补丁与 mysql-store.js 原始基准。不能忽略整个文件或放宽为部分核验。

发布必须沿用正式单任务锁、空闲检查、加密快照、确定 main SHA 的构建与隔离金丝雀。金丝雀只在带本次所有权标签的合成 MySQL 上验证新增迁移、幂等回执、原码失效、历史任务／已交付／人工待核对拦截、操作碰撞和八次真实 InnoDB 并发竞争。生产只执行新增迁移和只读验收，不创建测试码、订单或付款。

## 验证范围

定向单元测试验证外层状态、完整选择核对、部分成功、超时、落账失败、重启、原始备注和归属；原生模块验证事务回滚契约、资格、回执和新增迁移。离线浏览器调用真实外层处理函数验证草稿、状态变化重核对、失败恢复、原码隐藏、归还记录，以及 1440／768／390／320px、深浅主题。

真实事务竞争以正式发布前的远端隔离金丝雀回执为准。真实业务归还、付款和订阅变更不作为发布验收操作。
