# 充值码提取后的归还管理方案

正式续做补充：用户后续明确要求完成并发布，本方案已实施为 [未使用充值码归还](../RECHARGE_CODE_RETURNS_20261108.md)。下文保留原诊断与待批准阶段证据，最终发布结果以本轮回执为准。

## 结论

增加逐码归还及批量归还，未使用只是必要条件；真正归还成功还必须确认没有在途使用、原码已经失效，并留下原领用与归还回执。员工不能只在界面被移除领用关系，手里的旧码却仍可兑换。

优先复用“充值码提取”的申请记录与“我的充值码”页面，以右侧抽屉完成明细、归还核对和结果查看。发放、使用、归还各自保持独立状态，允许一批码只归还其中未使用的部分。

## 当前实现核查

项目为本独立工作区，分支 `codex/customer-email-product-isolation-20261108`，HEAD `43aed364f063c8e1572f72a13c99119edfa5d2ac`，此前未提交修改全部保留。

- `frontend/order-operations.js`：充值码提取只有申请及批准／驳回／重新核对；已发码行没有归还入口。“我的充值码”按未使用、已使用、处理中与待确认展示，目前主要操作是复制。
- `server/recharge-code-requests.mjs`：已有申请、审核、发码回读和状态读取；没有归还动作。使用状态从线上代充服务读取；上游失败、缺记录或套餐／类型异常映射为 `unavailable`，不能视为未使用。
- `server/order-recharge-client.mjs`：现有客户端只开放所需读取及导入码操作，没有撤销／冻结／归还的方法。
- 当前审核会生成新随机码再导入上游，不是从本系统已有的有限库存池扣码。此次不能凭空创建库存余额或资金退款；归还先体现为旧码失效、领用解除及已归还数量，下一次领用仍沿用原申请审批流程生成新码。
- 当前发放归属通过申请的 `codes` 列表关联申请人，`server/recharge-order-sync.mjs` 还会调用 `lookupRechargeCodeOwner()` 定位订单人员。归还不能删除原归属，否则后续核对或历史订单同步会失去依据。

只读核对固定原版 `codexdaichong@f4d7761e0036892e6dd68ec64c5447b513ca37da`：其 `server.js` 的码删除入口直接调用 `mysql-store.js` 的 `deleteCdk()`，后者按码删除，没有在同一操作中检查未使用状态、任务占用或并发兑换。现有 `listCdks()` 的 processing 主要来自 running 任务，单次列表快照本身不能阻止之后启动的新任务。

因此不能采用“先读 unused → 普通删除接口 → 本地记已归还”的实现。现有删除操作不是合格的归还确认能力，也不应通过删除业务历史来替代归还。

## 页面规划

### 充值码提取：申请记录

保留申请表单与原申请记录。记录标题右侧放“我的充值码”“归还记录”等就近入口，不单独增加空操作行。

申请表增加归还相关派生信息：已发码数量、可归还数量、已归还数量及领用汇总状态。宽度不足时以紧凑摘要承载，不压缩成不可读列。

| 发码后的情况 | 行内呈现 |
| --- | --- |
| 有可归还项 | 明细、归还（N） |
| 部分使用、部分可归还 | 部分可归还，明确 N 条可归还及其他数量 |
| 全部已使用或处理中 | 可归还 0，显示禁用的“无可归还项”及可查看原因的明细 |
| 有状态不明项 | 显示待核对数量；状态不明项不能被选入归还 |
| 已全部归还 | 显示“全部归还”，保留明细及归还记录 |

审批状态仍表达待审核、发码核对、已发码、已驳回；“部分归还／全部归还”是领用汇总，不将已发码申请改成已驳回，也不篡改原申请数量。

### 我的充值码

作为逐码操作的主要入口，提供状态页签与右侧搜索／套餐筛选／刷新。支持选择可归还项后批量归还，单行提供归还入口。

列包括：充值码标识、套餐、领码人、原申请／发放批次、发放时间、使用状态、归还资格／原因、归还状态、操作。已归还码保留历史标识并移入相应分类，不继续出现在可用码列表或普通复制结果中。

### 归还抽屉

标题“归还充值码”，说明收进标题右侧帮助图标。内容是逐码核对表与选填的归还备注，底部显示“已选 X／可归还 Y／被阻止 Z”及取消、确认归还。

- 按每个领码项的稳定编号操作，不能把页面显示序号或码尾四位当作唯一身份；相同尾号、套餐和不同申请必须能够区分。
- 一批可部分归还，不可归还行保留并显示原因；只允许勾选明确可归还的项。
- 点击确认前刷新资格；若任一已选项状态变化，更新核对表并要求重新确认，不静默只执行剩余项。
- 提交后处理结果逐项显示。跨服务可能只有部分项完成，必须如实列出成功／未完成／待核对项，不能把整批显示成全部成功或全部失败。
- 保存失败保留输入和选择；关闭及返回复用现有会话草稿。临时验证码等不纳入草稿；归还后旧码不再由可用列表重放。

### 归还记录

以一行一项记录原申请、套餐、原领码人、归还操作人、归还时间、说明、处理状态和核对入口。搜索和筛选与操作同排，支持分页；从原申请、我的充值码及归还结果都能打开同一条记录。

## 归还资格

| 当前情况 | 是否允许归还 |
| --- | --- |
| 本次有效领用、上游确认未使用、无任务及未解决业务关联 | 可进入归还流程，失效确认完成后才算成功 |
| 已使用／存在已确认成功结果 | 不允许，显示已使用原因 |
| 排队、执行中、请求已受理但尚未结束 | 不允许，不取消任务、不重复提交充值 |
| 失败但有付款／订阅结果不明 | 待核对，不能仅因码显示 unused 就归还 |
| 上游超时、状态缺失、重复码或套餐不一致 | 待核对；不得按未使用处理 |
| 已交付／出库且交付关系未解除 | 阻止并说明需核实原交付，不仅依据 unused 判断 |
| 已归还或正在归还 | 不重复处理；回读原操作及结果 |
| 不属于当前可处理范围或不属于本系统可追溯发放 | 拒绝；适用现有归属边界，不本轮放宽权限 |

归还不会停止正在执行的充值任务，不触发退款、银行卡释放、订阅修改或订单撤销。

## 关键闭环与实施前提

1. **必须使旧码失效**：仅本地标“已归还”、从列表隐藏、改领码人或设置 shipped 都不能替代上游失效。旧码以后不重新启用、不原样转交另一人；重新发放采用新码。
2. **归还与兑码必须互斥**：提交时须通过受支持的服务能力同时核对未使用、在途任务及撤销条件，确保一个码不会同时被归还和受理充值。只有前端按钮锁或当前 Node 进程中的 Set 不足以覆盖多进程、重启及其他兑码入口。
3. **先记可恢复操作，再做外部处理**：使用稳定归还操作编号，记录核对中／待确认阶段及目标领码项；上游处理后读取确认，再结束领用。超时或本地落账失败时保留待核对，按同一操作回读，不能盲目重发、恢复可用或重复计数。
4. **同一操作幂等**：重复点击、重试和重启都返回原结果，不重复归还、不重复发新码。批量结果按项登记及汇总。
5. **保留人员与历史**：原申请人、批准人、领码人及历史使用归属保持可追溯，归还另记实际操作人。订单按任务受理时的归属定位；归还不能把历史订单改给其他人，不能删除原代码与原领码人之间的审计依据。
6. **切断旧展示路径**：当前 `visibleRequest()` 会向申请人返回全部已发码字符串，`listIssuedCodes()` 和“我的充值码”的复制同样需识别归还状态。不能只改一个页面就让旧码继续从原申请响应中作为可用码返回。

目前未发现能够直接复用、满足第 1—3 条的原子撤销／归还接口。后续实施先验证上游是否提供该能力，或外围接入能否在覆盖所有兑码入口的前提下提供等效保证；不能把当前普通删除接口当作已具备该能力。

原版充值核心受固定源码约束。本方案不授权修改其付款、重试、任务或数据表逻辑；若验证结果要求新增核心操作或数据库结构，先单独说明具体差异、测试与影响，再按授权实施。能力未具备前归还入口应明确不可用，不能先做可点击界面并宣称完成。

## 后续验收

- 多码申请中只归还部分未使用码：其他码、原申请数量及原发码历史保持不变。
- 全部已使用、处理中、付款结果不明、上游不可用、缺码、重复码、套餐冲突都有明确阻止原因，0 条与有可归还项都可辨认。
- 归还与使用同时发生时最多一方成功；已经受理的任务不被归还操作中断，归还成功的旧码在全部兑码入口失效。
- 外部已完成但本地回执丢失、部分完成、服务重启、重复提交、跨进程并发可回读恢复，不重发或复活旧码。
- 原申请响应、我的充值码、复制、查询及订单同步均使用一致的归还与归属信息；新码不继承其他员工的历史。
