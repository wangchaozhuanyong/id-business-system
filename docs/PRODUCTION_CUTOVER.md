# 独立新版正式切换

1. **冻结候选。** 从独立 Git 提交生成制品，记录 SHA 和 SHA-256。Node 使用固定版本，代充前端从固定的 Codexdaichong 提交构建。测试数据、运行配置和凭据通过独立渠道管理。
2. **隔离预演。** 在 AWS 使用独立进程或容器和全新私有目录，保持正式入口指向旧系统。先核对 HTTPS 域名、登录、员工权限、库存保存和重启、订单录入、备份恢复。再单独验收 Vendure、代充、邮箱和工具对接。发现历史合约无法接入时，保留旧入口直到替代方案验证通过。
3. **准备正式运行。** 管理员通过服务器终端初始化。反向代理用有效证书终止 HTTPS，保留请求的正式 Host。应用监听私有地址，只有受管反向代理可以访问。密钥和持久化目录由正式服务账号管理。单实例运行，业务库与其加密密钥成对备份，员工账号文件由单独的私有备份保护。预演恢复时使用副本。
4. **切流。** 先核对旧站活动代充任务和公开回调。临近切换重新核对生产版本，取最新 MySQL 快照，保存本地并验证摘要和隔离恢复。新站通过同域 HTTPS 的最终烟测后，再按受管流程替换入口。若切换失败，恢复原入口并核对切流期间的独立新版新增业务。
5. **收尾。** 核对线上 SHA 和实际业务读写后，将独立新版提交纳入 GitHub 的发布流程。清理旧运行资源前保留可恢复的旧站制品和旧数据。主分支使用普通提交替换目录。

正式数据目录必须由服务账号持有，权限为 `0700`。以下为在受管内部环境运行的命令，目录应已按上述要求准备。

```sh
node server/setup-local-admin.mjs --data-dir /app/.runtime/production --email admin@example.test
node server/preview.mjs --data-dir /app/.runtime/production --public-origin https://admin.example.test --port 4347
```

正式模式启动时需要已初始化账号。业务接口需要会话，登录和写入只接收正式 HTTPS 来源。上线前用真实 HTTPS 域名检查登录、退出、库存保存和刷新，确认网页初始化入口关闭。公开查询、采集及 OAuth 回调由各自的访问规则验证。
