# 独立新版正式切换

1. **冻结候选。** 从独立 Git 提交生成制品，记录 SHA 和 SHA-256。Node 使用固定版本，代充前端从固定的 Codexdaichong 提交构建。测试数据、运行配置和凭据通过独立渠道管理。
2. **隔离预演。** 在 AWS 使用独立进程或容器和全新私有目录，保持正式入口指向旧系统。先核对 HTTPS 域名、登录、员工权限、库存保存和重启、订单录入、备份恢复。再单独验收 Vendure、代充、邮箱和工具对接。发现历史合约无法接入时，保留旧入口直到替代方案验证通过。
3. **准备正式运行。** 管理员通过服务器终端初始化。反向代理用有效证书终止 HTTPS，保留请求的正式 Host。应用监听私有地址，只有受管反向代理可以访问。密钥和持久化目录由正式服务账号管理。单实例运行，业务库与其加密密钥成对备份，员工账号文件由单独的私有备份保护。预演恢复时使用副本。
4. **切流。** 先核对旧站活动代充任务和公开回调。临近切换重新核对生产版本，取最新 MySQL 快照，保存本地并验证摘要和隔离恢复。新站通过同域 HTTPS 的最终烟测后，再按受管流程替换入口。若切换失败，恢复原入口并核对切流期间的独立新版新增业务。
5. **收尾。** 核对线上 SHA 和实际业务读写后，将独立新版提交纳入 GitHub 的发布流程。清理旧运行资源前保留可恢复的旧站制品和旧数据。主分支使用普通提交替换目录。

正式数据目录必须由服务账号持有，权限为 `0700`。以下为在受管内部环境运行的命令，目录应已按上述要求准备。

```sh
node server/setup-local-admin.mjs --data-dir /app/.runtime/production --email admin@example.test
node server/preview.mjs --data-dir /app/.runtime/production --public-origin https://admin.example.test --port 4347
```

正式模式启动时需要已初始化账号。业务接口需要会话，登录和写入只接收正式 HTTPS 来源。上线前用真实 HTTPS 域名检查登录、退出、库存保存和刷新，确认网页初始化入口关闭。公开查询、采集及 OAuth 回调由各自的访问规则验证。

Vendure 的验收分两步。先用隔离宿主验证原路径、字段、重复提交与重启回读，再用独立正式库和专用服务凭据核对商城来源、兑换码归属和历史任务回执。正式库通过只读预检后，仍须确认执行器的启动、重启及资产锁处理方式，再启用新单。执行结果未知时，按原任务核对，禁止自动补建任务。正式域名在商城和实际收件验收通过后切换。

用当前代码准备锁定上游副本并安装依赖后，对已初始化的专用代充库运行 `runtime.mjs preflight-production [副本目录]`，再用 `runtime.mjs start-production [副本目录]` 启动。服务监听回环并持有 MySQL 运行锁。连接失去运行锁时服务停止，重启前重新检查未结任务、未登记任务的已占用兑换码和资产锁。正式运行只挑选空闲资产，遗留占用由操作人员按原任务核对。旧运行副本需要重新准备。

正式 Caddy 站点在兜底路由之前导入 `deploy/caddy/vendure.caddy`。`ID_VENDURE_SOURCE_IPS` 使用已核实的商城服务出口 IP，以空格分隔。来源按 Caddy 实际 TCP 对端检查，部署前须确认该入口由 Caddy 直接接收，代理出口地址不能代替商城地址。Caddy 和商城任务服务使用同一网络命名空间，`ID_VENDURE_LOOPBACK_PORT` 指向任务服务的商城端口。任务服务另外校验商城凭据和用户地址头，执行器端口仅供回环调用。启用前验证正常来源、伪造转发头、错误密钥、旧任务查询和上游失联。

商城任务服务默认维护模式，允许验码和回读已接收任务，暂停接收新单与执行领取。待旧任务的可查询性、正式库、执行器和重启处理全部验收后，才在私有配置中启用 `acceptSubmissions`。代理不重试充值提交，网关超时或失联时应查原兑换码与任务，确认是否已接收。

旧商城回执通过私有配置的 `legacyReceipts` 只读挂载。每条包括原 `id`、`plan`、`status`、毫秒精度 `updatedAt`，以及按新版存储密钥计算的 `oldTokenRef`。仍被原兑换码占用的回执同时保留 `codeRef` 和 `codeStatus`。摘要为 HMAC-SHA256，输入依次为用途（`legacy-task` 或 `code`）、零字节、去除前后空白的原值。只导出确认完成、确认失败或明确转人工核对的回执。新服务允许商城用已有任务凭证查询原编号，同时给新的查询响应签发凭证。已导入的兑换码不再分配或执行。失败后已释放兑换码的回执仅保留凭证查询，新的受理资格由独立配置决定。导出过程不得输出原兑换码、原凭证、会话或旧库密钥。
