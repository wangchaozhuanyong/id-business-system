# V2 加载、体验与多人并发审计（2026-08-30）

## 结论

本轮已完成代码库、隔离测试环境和 AWS 生产环境只读容量审计。生产构建的初始 CSS 为
**8.30 KB gzip**，初始 JS/modulepreload 为 **132.35 KB gzip**，均低于当前门禁的 45 KB 和
145 KB；29 个页面异步 chunk 均低于 25 KB gzip。相较审计初值 141.01 KB，首屏 JS 减少
8.66 KB，门禁余量由 3.99 KB 扩大到 12.65 KB。

核心业务写入继续由 `V2CommandTransactionManager` 统一执行，默认使用 Serializable 事务，在事务内
递增精确数据范围版本，只对具有稳定幂等证据的命令执行冲突重放。Prisma schema 当前包含 11 个唯一
幂等键字段，财务 MySQL 验收保留 8 路并发只生成一个业务结果的真实数据库测试。

本轮另修复两个此前未被统一事务内核覆盖的高风险后台管理竞态：

1. 员工资料、启停和角色调整现在必须提交读取时的 `updatedAt`，后端在撤销会话或修改角色前先执行
   原子版本抢占。旧快照提交返回 409，不再覆盖其他管理员刚完成的修改。
2. IP 白名单新增、修改和删除现在使用同一数据库事务锁串行化“防锁死校验 + 写库”，编辑和删除同时
   校验 `updatedAt`。业务记录、审计、实时范围版本在同一事务提交，提交后才广播安全范围事件。

真实登录运行时验收也已完成：使用一次性 MySQL、生产前端构建和两个彼此隔离的浏览器上下文，逐页
访问全部 24 个受保护路由并保存截图；员工和 IP 白名单的双端并发写入都得到一个 200 与一个 409，
员工胜出结果 205 ms 内在两个浏览器一致可见。SSE 连接建立后固定版本轮询为 0，页面
整页刷新为 0。

AWS 当前生产主机也已执行无认证、无业务写入的渐进只读抽样。2 vCPU、1.9 GB 内存规格下，
`/api/health/ready`（包含真实 MySQL `SELECT 1`）在并发 1、5、10、20 共 560 次请求中全部返回
200；MySQL 历史最大连接数为 16/151，Prisma 单 API 实例连接池上限为 10。该结果证明当前低压力
读探针没有错误或连接池耗尽，但不能替代登录后业务接口、真实写入和长时间生产 SSE 的维护窗口压测。

运行验收同时发现并修复两处只会在 MySQL 真实执行时暴露的 SQL 方言问题：事务命名锁的 INSERT 以及
业务监控原生查询错误使用 PostgreSQL 双引号标识符，导致登录或业务监控在 MySQL 返回 Prisma P2010。
两处现已保留 PostgreSQL 行为并在 MySQL 运行时转换为兼容 SQL，且增加回归测试。

### AWS 生产只读容量抽样

生产只读巡检复用了权限为 `0600` 的本机连接文件，仅访问健康端点、容器资源和 MySQL
`performance_schema`，没有登录、写业务表、修改配置或部署。

- EC2：2 vCPU、1,909 MB 内存、磁盘使用 67%；巡检时 load average 为 0.00/0.03/0.05。
- 容器：API 约 124 MiB、MySQL 约 298 MiB、管理端约 5 MiB，服务均为 healthy。
- 连接池：Prisma `connection_limit=10`、`pool_timeout=20`；MySQL `max_connections=151`，历史峰值
  16（10.6%），巡检时连接 11、运行线程 2、拒绝连接 0。
- 渐进探针：并发 1/5/10/20 共 560 次 readiness 请求全部为 200；对应 p99 为
  370/412/1,018/336 ms。并发 10 阶段有网络抖动，但没有超时、错误或连接峰值增长。
- 空闲 30 秒复测：连接数只增加 4（包含两次审计连接和例行健康探针），`Aborted_clients` 未增加。

MySQL 原生 `slow_query_log=0`、`long_query_time=10`。本次新增每 5 分钟执行的
`performance_schema` 只读摘要，避免慢查询文件无限增长；它观测连接占用、异常断连增量和最近
10 分钟在线业务 SQL digest，不输出 SQL 正文或参数。首次真实 SSH 运行显示连接使用率 7%、
`Aborted_clients` 增量 1，最近最慢业务 digest 为 11 ms，均未触发告警。历史摘要中最慢的
105 次语句平均 2.75 秒、最大 3.93 秒，已确认是每 30 分钟备份执行的
`SELECT SQL_NO_CACHE *` 全表读取，而不是在线业务 SQL；巡检窗口内可识别的业务查询最大约 24 ms。
`Aborted_clients` 累计值偏高，因此新巡检按每个 5 分钟窗口的增量告警，不再只看累计值。

### 双浏览器实时与并发结果

- 员工新增提交后，两个浏览器无需刷新即看到新记录，最慢可见时间为 243 ms。
- 两端基于同一员工旧版本同时保存：HTTP 状态为 `[409, 200]`；胜出值 205 ms 内在两端一致可见。
- 两端基于同一 IP 白名单旧版本同时保存：HTTP 状态为 `[409, 200]`；最终值与成功请求一致。
- 两个浏览器各建立 2 次 SSE 连接，次数来自逐页导航重连；连接成功后的固定版本轮询均为 0。
- 两个浏览器的整页刷新次数均为 0，实时更新通过范围事件和后台查询失效完成。

### 5 分钟 SSE 稳定性

在隔离 API 与一次性 MySQL 上保持单条认证 SSE 连接 300 秒：收到 1 个初始快照、11 个心跳和
并行验收产生的 10 个变更事件；首快照 0.4 ms，最大心跳间隔 25,002.5 ms，期间无断连、无超时，
最终正常注销。心跳间隔与服务端 25 秒配置一致，心跳本身不查询业务表。

## 核心员工工作流审计

### 1. 进入系统与首屏

任务：登录后尽快看到稳定的应用结构和当前页面。

- 已通过：Vue 根应用先挂载中性启动壳，会话检查和路由代码加载不阻塞 `mount`。
- 已通过：Element Plus 使用按需 resolver，不加载全量 CSS。
- 已通过：路由页面按 chunk 拆分，只在悬停、键盘聚焦或点击意图出现后预取。
- 已通过：Chunk 加载失败保留当前稳定页面，并提供受控恢复路径。

### 2. 打开列表、搜索、排序和分页

任务：快速读取数据，切换条件时不闪空表、不跳页。

- 已通过：所有真实业务页面统一使用 `useV2ModuleQuery` 与规范化查询 key。
- 已通过：同身份、同范围、同 key 的并发读取复用一个请求；旧请求不能覆盖新条件结果。
- 已通过：筛选、排序、分页时保留最后成功内容，返回成功后再原子替换内容和分页状态。
- 已通过：首次加载显示内容形状骨架；已有内容刷新超过 120 ms 后只显示区域顶部进度线。
- 已通过：查询缓存仅在内存中保存，最多保留 200 个非活跃条目，切换身份时整体清除。

### 3. 编辑并提交业务数据

任务：清楚知道正在提交、提交失败可重试，重复点击不产生重复业务记录。

- 已通过：业务写入由统一事务管理器处理，审计、账本、业务记录和范围版本在同一事务内提交。
- 已通过：可重放命令必须同时声明稳定幂等键和 replay；不可重放命令在类型层禁止冲突自动重试。
- 已通过：金额继续使用 Decimal 领域类型，不以 float/double 参与业务计算。
- 已通过：前端写请求不会在认证短暂故障后自动重放，避免用户不知情地重复提交。

### 4. 两名管理员同时编辑同一员工或白名单

任务：不能静默覆盖，也不能因并发校验产生系统锁死。

- 已修复：员工修改先比较页面版本，再以条件 `updateMany` 原子抢占版本；抢占失败时事务内没有会话、
  角色或审计副作用。
- 已修复：白名单修改和删除携带页面版本；所有白名单安全变更共享
  `security:ip-whitelists` 事务锁，第二个请求必须在第一个提交后基于最新集合重新校验。
- 已通过：角色修改已有 `expectedUpdatedAt` 条件更新；冲突返回明确的刷新重试提示。

### 5. 其他人员提交新数据

任务：当前页面无需手工刷新即可看到已提交数据。

- 已通过：连接正常时使用受 JWT 保护的 SSE，仅在真实提交后推送 scope/version；没有新数据时只发送
  不查询业务表的连接心跳，不固定刷新业务列表。
- 已通过：事件到达后只标记受影响查询为 dirty，并在 100 ms 内合并同范围事件；当前页面保留内容并
  后台刷新。
- 已通过：SSE 断开后才启用 15 秒版本补偿；重连、恢复联网或页面恢复可见时立即核对一次。

### 6. 加载失败、提交冲突和断网

任务：用户能理解当前状态，不误把旧数据当作已保存结果。

- 已通过：首次读取失败、已有内容刷新失败、空状态和参数切换分别展示，不把失败显示成“暂无数据”。
- 已通过：409 版本冲突显示服务端业务提示，要求刷新后重试，不自动覆盖或自动重放。
- 已通过：已验证会话遇到短暂 503 时保留最后内容并切为只读；恢复后重新验证权限和失效查询。

## 已确认的优势

- 首屏 CSS 只占门禁约 18%；初始 JS 占 145 KB 门禁约 91%，还剩约 12.65 KB gzip 余量。后续新增
  首屏依赖仍必须先拆分或延迟加载。
- 路由、数据和加载反馈已经分层；不会用整页遮罩掩盖可继续阅读的旧内容。
- 核心业务写入具备事务、锁、幂等、审计和冲突语义，不依赖前端“按钮禁用”保证正确性。
- 实时更新按数据变化触发；连接正常时没有固定时间刷新业务 API。

## 数据库与接口变更

本轮没有新增表、字段、索引或 migration。现有接口增量要求如下：

- `GET /api/realtime/events`：新增受 JWT 保护的 SSE 快照、变更事件和 25 秒连接心跳。
- `PATCH /api/v2/employees/:id`：新增必填业务版本 `expectedUpdatedAt`。
- `PATCH /api/v2/security/ip-whitelists/:id`：新增必填业务版本 `expectedUpdatedAt`。
- `DELETE /api/v2/security/ip-whitelists/:id`：新增查询参数 `expectedUpdatedAt`。

新增运行验收脚本和 API 性能探针只读取本地环境配置，不输出账号、密码、JWT 或数据库连接串；一次性
MySQL 数据只用于隔离验收，不触碰生产数据。
