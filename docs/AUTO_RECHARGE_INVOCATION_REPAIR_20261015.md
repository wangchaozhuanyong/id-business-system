# 比特窗口调用与官网登录识别修复

用户要求正常执行，并能准确指出失败位置。本次基于已实测页面对应的 `e474bc8ed3ecc1a942f2eeb54bccab30570ae2af` 建立项目内隔离候选，未改主目录的并行工作。

## 已确认的根因

1. 比特客户端先打开的原窗口进程只有 `--remote-debugging-port=0`。网站的打开接口返回成功，但随后 WebSocket 控制握手失败。关闭本次没有付款操作的原窗口，再由系统打开后，进程带有精确网站来源的 `--remote-allow-origins`，控制连接与账号核对通过。不能把“打开接口成功”当作“窗口已可控”。比特官方接口将 `args` 定义为浏览器启动参数，见[接口说明](https://doc.bitbrowser.cn/api-jie-kou-wen-dang/liu-lan-qi-jie-kou)。
2. 真实官网新版账号菜单使用 `aria-label="打开个人资料菜单"`，聊天输入使用可编辑的 `div[role="textbox"][aria-label="询问 ChatGPT"]`；原有测试标记已不存在。原识别函数因此在已经可用的页面上持续返回“加载中”。在同一个真实窗口上只读运行修复前后函数，结果分别是 `page_loading` 与 `page_ready`。
3. 旧结束回执把窗口控制失败也统一记为官网会话恢复失败，导致排查位置不准确。

## 代码改动

- `bitbrowser-login-page.ts`：兼容新旧官网控件，继续要求正向账号控件与可编辑聊天输入均可用，保留隐藏、禁用、忙碌和遮罩检查。身份核验仍由原流程独立完成。
- `bitbrowser-direct-login.ts`、`bitbrowser-direct-api.ts`：仅对已核实归属的原窗口读取存活进程；原进程已运行且首次控制握手失败时，明确说明原窗口未建立网页控制连接，并给出关闭该原窗口后由本页打开的处理步骤。不自动重启、删除或新建窗口，不把取消误报为连接故障。
- `useBitBrowserDirectOpen.ts`、`recharge-presentation.ts`：控制连接失败与身份已核实后的页面就绪失败分别记录和显示阶段。
- 四个既有测试文件补充新官网 DOM、隐藏／不可编辑反例、原进程状态、控制失败、取消保留和结束回执分流。
