# ID 业务管理系统平台开发与上线方案

## 1. 当前结论

当前系统适合进入受控试运行，但还不适合宣称“全功能正式生产系统”：

- 注册表共有 22 个模块，其中 13 个是真实业务模块，9 个仍是只展示规划说明的 `planned` 页面。
- 订单、ID、加卡、续费、汇率等核心业务已经具备实际能力。
- 多币种财务页面已经接入，但生产 migration、历史回填、期初余额和遗漏开支仍需业务确认。
- 通用回收站、数据恢复、清理任务、员工管理、角色管理、审计查看和安全中心仍未形成可操作闭环。
- 当前唯一真实的自动保留清理是汇率历史清理，不等于已有通用“清理数据”功能。

本方案只按新系统现有业务设计，不恢复旧网站的通知、兑换码、平台接口、Apple 执行器或其他已排除
功能。

## 2. P0：正式上线前

### 2.1 固化业务与财务基线

1. 完成多币种财务 migration 和历史日记回填。
2. 由业务负责人确认 CNY、MYR、USDT 期初余额、供应商余额和遗漏开支。
3. 经营分析在确认前持续显示“历史数据未完整”，不得对外宣称完整生命周期利润。
4. 用真实数据完成加卡、订单完成、退款、ID 收回、手工续费、财务日记和审计追溯。

### 2.2 生产备份与恢复

1. 使用真实 Supabase/PostgreSQL 项目的托管备份或时间点恢复能力，核对数据库项目身份。
2. 发布单记录备份引用、生成时间、migration 水位、核心表行数和恢复演练引用。
3. 把备份恢复到新建隔离库，校验 schema、约束、核心数据、账务平衡和敏感字段可解密性。
4. 禁止把旧 dump 直接覆盖在线库；禁止在生产执行 seed、reset、重复基线或全表回填。
5. 应用发布只执行向前兼容 migration；数据库问题使用前向修复，不跟随应用版本自动回滚。

### 2.3 审计、账号、权限和会话

开发顺序固定为：

1. 审计日志：接入现有分页接口、筛选、变更详情、敏感访问日志和导出留痕。
2. 角色权限：第一版只维护固定角色和权限矩阵，不开放任意自定义角色。
3. 员工账户：管理员开通、停用、分配角色、首次强制改密和强制退出，不提供公开注册。
4. 安全中心：先做登录记录、在线会话、退出其他设备和管理员强制下线。
5. 我的账户：复用现有修改密码能力，补个人基本信息和自己的登录设备，不重复建设密码页面。

Supabase Auth 与业务用户的跨系统写入必须提供补偿流程。停用员工时必须同时停用
`V2AuthIdentity`、撤销全部会话并写审计。生产统一使用 Supabase MFA；本地 TOTP 和 IP 白名单在
没有防自锁方案前不开放。

### 2.4 回收站最小闭环

第一版回收站只覆盖已经采用软删除的员工、选项、客户、ID 和订单。恢复时只清除受控删除状态，
并检查唯一键和关联状态；如果新数据已经占用唯一键，进入人工冲突处理，绝不覆盖新记录。

下列数据禁止进入普通回收站或硬删除：

- ID 报损记录
- 余额流水
- 供应商资金流水
- 财务日记
- 礼品卡反向记录
- 已被业务账务引用的汇率快照

这些数据只能通过反向流水、冲销或专用更正流程纠正。

## 3. P1：上线后第一阶段

### 3.1 数据治理

先开发“影响预览 → 审批 → 执行 → 结果审计”，再开放任何清理按钮：

- 预览固定记录 ID、实体类型、版本、删除时间、依赖阻塞原因和不可变 `scopeHash`。
- 审批绑定具体预览版本；发起人不能审批自己的任务。
- 执行只处理已审批明细，并使用 `id + updatedAt/版本` 条件更新。
- 预览后有新修改的记录标记 `stale_skipped`，不得覆盖。
- 每批 100–500 条，单批事务，具备幂等键、检查点、暂停和失败重试。
- 记录候选、成功、跳过、冲突、失败数量以及审计编号。

第一阶段只支持软删除数据恢复和已明确保留期的技术数据清理。通用硬删除保持关闭。

### 3.2 仪表盘和监控

- 仪表盘只展示可追溯的今日业务、到期风险、供应商负余额和财务完整性状态。
- 业务监控复用订单状态、续费预警、汇率失败和资金风险，每个异常必须能返回来源记录。
- 系统监控先接健康端点、数据库就绪、migration、汇率 Cron、Realtime 降级和发布版本。
- 团队动态只显示高风险审计摘要，避免与审计日志重复。

## 4. P2：可延期或合并

- 自定义角色、批量员工导入、管理员重置 MFA 和 IP 白名单。
- 通用导入中心；现阶段继续由各业务模块做带校验的导入。
- 通用硬清理、审计归档和独立监控大屏。
- 独立“我的账户”页可合并到账户菜单。

如果确认合并或删除现有规划页，必须先同步修改 `docs/V2_PRODUCT_SCOPE.md`。

## 5. 防止旧数据覆盖新数据

### 5.1 普通任务

```text
读取当前版本
  → 生成不可变预览和 scopeHash
  → 独立审批
  → 按 id + 版本条件执行
  → 新版本记录 stale_skipped
  → 分批提交和审计
```

禁止使用“按旧备份内容全表覆盖”“先删后导”“无版本条件 upsert”或任意 SQL 清理。

### 5.2 灾难恢复

```text
冻结写入并记录水位
  → 旧备份恢复到隔离库
  → 对比线上备份后新增数据和不可变流水
  → 增量重放或人工合并
  → 账务与权限验收
  → 切换连接
  → 原生产库只读观察
```

只有应用代码可以按上一 Worker 版本自动回滚；数据库不自动回滚。

## 6. Git 与全量发布流程

1. 在独立开发分支只提交本次认证、发布和计划范围内的文件，排除并行产生的其他业务改动。
2. 分支推送后创建 PR，由 CI 完成 lint、typecheck、test、build、Prisma 和架构检查。
3. PR 审查通过后合并受保护 `main`，再次确认 `HEAD = origin/main` 且工作树干净。
4. 完成生产数据库备份、隔离恢复演练、schema drift 和 migration 核对。
5. 先关闭 Realtime Broadcast，发布 API 与管理端同一 Worker 版本。
6. 执行首页、健康端点、只读巡检账号、权限拒绝、强制改密和核心只读接口验收。
7. 巡检失败自动回滚到发布前唯一承载 100% 流量的 Worker 版本，并再次验收。
8. 发布稳定后再按功能开关逐项启用，任何数据库修复都走新的前向 migration。

## 7. 正式上线门禁

- 13 个真实模块已用真实角色验证前端可见性和后端越权拒绝。
- 财务 migration、历史回填、期初余额、遗漏开支和账务平衡已确认。
- Supabase 身份、首次改密、会话撤销、MFA 失败关闭和敏感字段审计已验证。
- 托管备份有效，隔离库恢复演练成功，旧数据不会覆盖备份后的新记录。
- 工作树干净，发布提交与受保护 `origin/main` 一致，必需 CI 全绿。
- API 与管理端同批发布，线上健康、只读巡检和核心业务冒烟通过。
- 回滚目标唯一、可执行且回滚后巡检通过。

任一门禁未满足，只能称为“代码已准备”或“受控试运行”，不能称为全量发布成功。
