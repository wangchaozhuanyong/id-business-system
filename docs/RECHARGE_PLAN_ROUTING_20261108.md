# 套餐支付地区与出口选路

用户在 2026-11-08 明确批准本次选路调整，并要求修复后发布、继续支付页调试。该授权只对旧“原文件完全不变”要求增加下述例外；原 Checkout API 400 问题推迟处理。

## 执行规则

| 套餐 | 初始支付地区 | 币种 | 必需出口国家 |
| --- | --- | --- | --- |
| Plus | 菲律宾 PH | PHP | PH |
| Pro 100 | 埃及 EG | EGP | EG |
| Pro 200 | 菲律宾 PH | PHP | PH |
| Pro 500 | 埃及 EG | EGP | EG |

管理员可为四种套餐各选一个支持的地区。服务端读取配置而非信任请求的 country/region。只有启动新的原浏览器充值或支付页调试时生效，第三方代充 API 供应商流程保持原样。旧套餐未配置则停止，不猜测对应关系。

启动前从启用代理中实测 Cloudflare HTTPS trace 的公网 IP/国家，不凭主机名或手填标签判断。已有匹配检测结果只用于优先排序，每次启动仍重新检测；每次选择最长 20 秒、单条最长 10 秒，检测失败不放行。检测结果记录国家、时间、来源、IP、延迟；不保存代理凭据。代理原配置只在数据库原位置保留，新增表内仅存配置 SHA-256 以识别失效记录，管理响应不返回该哈希。

非空代理池没有匹配启用代理就停止，不回退直连。完全空池才实测运行执行器的服务器直连出口，必须与套餐国家相同；不是用户 Mac/Windows 的 IP。单次原版执行尝试选中的线路解析 session 占位符一次，在子进程启动前复核并复用相同线路。原版要求下一轮外层尝试时，在原有取代理位置重新按已受理任务国家选择线路及 sticky session；不固定全部尝试使用同一代理。代理配置被修改/停用、国家漂移或空池状态变化即停止该次启动。开始执行后不增加监控、支付重试或强制终止。地区配置修改仅影响新任务，不改变已受理任务的国家。

出口检测历史只用于排序；历史读取失败时以本次实时检测为准。检测记录、代理检测状态和使用次数保存失败只输出固定的管理员提示，不把成功出口标为网络失败，不阻止有效线路启动。套餐配置及代理池/代理启用状态读取失败仍停止启动，不把读取失败解释为空池。没有实时国家证据时仍不放行。

付款前选路不通过时不查询银行卡可用性、不占用充值码、不创建充值任务。已受理任务运行前复核失败沿用原版异常清理。客户只收到“当前套餐的充值线路暂不可用，请联系客服处理。”；管理员可以看到不含凭据的选路原因。

## 核心边界与界面

固定上游 `f4d7761e0036892e6dd68ec64c5447b513ca37da` 保持独立。200 个文件全部进行内容、类型、权限核验，其中 197 个严格等于原版；三份批准差异以补丁和 manifest 的 Git blob/SHA-256 核验：

- `server.js`：新配置接口和启动前选路，原执行器参数增加地区/代理，不改支付步骤。
- `region-config.js`：新增 EG/EGP、地区名称、时区和语言元资料。
- `pricing-checkout.js`：只增加埃及国家名、币种识别元资料，不改导航、选择器或 API/UI 回退算法。

`index.js`、`payment-retry.js`、`stripe-payment.js`、`tax-free-address.js`、`mysql-store.js` 及依赖锁均逐字保持。账单地址库仍用美国，银行卡填写、换卡、重试及订阅核验完全沿用原版。

外围管理页增加四种套餐地区设置和服务器直连检测；代理列表显示实测国家与时间，检测按钮走同一检测器。支付页调试的地区只读、随套餐变化。配置保存用版本校验防覆盖，保留配置审计；更新配置需要外围敏感资料管理权限。补齐原版截图渲染引用缺失的 UI 函数，截图仍走统一登录接口，不拼接 token。

Vendure 仍只提交原兑换码/资料并读取安全进度；采集、订单录入和同步不改变、不重复或取消充值。现网商城维护状态不因发布开启。

新增出口检测需要最多 20 秒，商城仅对提交充值的 HTTP 请求增加 30 秒等待预算，其他查询时限不变；不增加充值重试。选路阶段明确返回 HTTP 409、固定代码和 `execution_started:false` 时可确定任务没有开始，商城显示失败并可由客户主动重新提交；缺少这份明确回执或网络中断仍待核实。

## 新接口和迁移

原私网管理鉴权下新增：`GET/PUT /api/admin/recharge-routing`、`POST /api/admin/recharge-routing/check-local`、`POST /api/admin/recharge-routing/proxies/:id/check`。公网只能经原统一登录网关访问，不开放原端口。检测不接受自定义目的 URL，避免代理检测成为任意网络请求接口。

`routing-migration.sql` 只新增 `id_recharge_route_config` 和 `id_recharge_proxy_checks` 两张模块表；原表、数据和迁移不更改。初始配置 INSERT IGNORE，不覆盖已有值。迁移入口为容器 `migrate-native-routing`，只在正式入口暂停、空闲核验和新鲜加密备份后执行；隔离金丝雀使用 `migrate-canary-routing`，不连接生产库。不自动执行生产回滚或删除新表。

### 2026-11-11 代理国家标注

代理导入仍走 `POST /api/admin/proxies`，请求包含 `proxies` 和必填的 `countryCode`。一批代理与标注在同一事务保存。重复线路已有相同标注时跳过，原线路未标注时补标，已标为其他国家时拒绝整批。列表补标及修改使用 `PUT /api/admin/recharge-routing/proxies/:id/country`，同时提交 `expectedCountryCode` 以保护并发编辑。

`proxy-country-labels-migration.sql` 在原版 `proxy_assets` 初始化后增加 `id_recharge_proxy_country_labels`。表内保存代理编号、国家码和标注审计，出口检测继续写入 `id_recharge_proxy_checks`。沿用上述迁移入口，成功回执为 `per-plan-routing-v2`。

浏览器充值先实时核验标注与套餐匹配的启用代理，再核验待标注的启用代理。标注为其他国家的代理不参与该套餐选路。实测一致才放行，原有空池直连规则继续适用。

### 代理类型标记

充值代理池与比特 IP 资料库共用 `modules/recharge/bitbrowser/proxy-types.mjs` 的四种类型。充值表单导入时把 `proxyType` 应用于当批所有新增代理。重复代理保留原类型，旧代理可在列表补录。旧导入客户端可以省略类型。

充值类型按代理编号写入现有 `app_config`，与导入同一事务，无需迁移。列表从路由管理接口的 `proxyTypes` 读取；修改使用 `PUT /api/admin/recharge-routing/proxies/:id/type` 并提交 `expectedProxyType`。类型是管理标签，套餐仍按国家和实测出口选路。

## 验证要求与边界

无本地数据库的测试覆盖：真实 trace 解析、套餐配置、空池与国家不匹配、同一 sticky 线路复核、配置/代理变更竞态、秘密脱敏、启动参数及选路失败不占资源、源码完整性、原版换卡及 API/UI 回退、调试截图终态恢复。

发布需通过远端合成数据库金丝雀、同 main SHA 制品和镜像核验、迁移回读、线上页面宽窄屏与权限验收。用户授权的 Session 调试只到支付表单，不能填卡、扣款、变更订阅或发外部通知。没有 EG 出口时不能将埃及套餐记为真实联通通过。国家一致也不能保证第三方 API 不触发风控。

代码、本地检查、远端 CI、正式发布和真实支付页结果分别记录在项目 backups/recharge-plan-routing-20261108，未实际完成的环节不得宣称通过。
