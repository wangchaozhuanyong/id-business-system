## 3. 数据与页面共用方式

### Vendure 邮箱数据作为这套功能的唯一来源

```text
ID 管理页面 → ID 后端（现有管理员校验、操作审计）
                         ↓ 专用邮箱对接接口
Vendure 管理页面 → Vendure 邮箱服务 → Vendure 现有邮箱数据

ID 买家查询入口 ─┐
                ├→ 共用查询页面 → Vendure 邮箱查询服务
Vendure 查询入口┘
```

不在两个数据库各维护一份相同邮箱，避免出现一边停用而另一边仍能查询、重置后旧码仍有效等问题。
“操作同步”定义为操作成功后另一端下一次读取可见，与本次对话确认的“另一边刷新后就能看到”一致。
页面在打开、切换页签、返回浏览器前台、手动刷新以及写入成功后读取最新数据；
两端一直开着时的自动实时推送不作为本期交付条件，不新增后台邮件轮询来模拟管理数据同步。
读取失败保留最后成功内容并显示更新时间和失败提示，不将旧内容标成已同步。

查询页复用 Vendure 现有 `portal-html.ts` 和 `portal-script.ts`，通过固定的同源入口提供给 ID；
不复制一份永久独立维护的模板。规划增加独立的中继查询入口，保留 ID 原有 `/mailbox` 的既有查询行为。
具体入口路径在接口阶段登记，不能覆盖旧路由后让原有查询码失效。
页面与脚本采用同一版本标识，资源和接口必须成套校验；服务不可用时显示明确错误。
入口转发限制到固定页面资源和确定的邮件查询操作，不开放任意 GraphQL、URL 或路径转发。
品牌参数、资源路径、返回入口、缓存和内容安全策略需要一起验证；查询码不得放入 URL 或访问日志。

两个管理端使用不同前端框架，不能直接把 React 组件放入 Vue。
本次统一页面结构、文案、字段顺序和操作行为；ID 管理页面使用现有 Vue 组件实现。
管理端代码自动共享属于额外的共用组件工程，不应把两份相似页面描述为一份共享组件。
统一布局以模块内容区为验收边界，两站的整体导航和登录外壳维持所属项目的现有结构。
凡本次为满足表单规则、分页、冲突提示而调整的模块布局，两端都应用同一设计规则，不只改 ID 一侧。

### 现有 ID 邮箱数据兼容

ID 现有 Gmail、Microsoft 以及已入池的 iCloud 邮箱继续使用现有查询与授权流程，入口清楚区分来源。
本次首先接入 Vendure 的 iCloud 中继功能；不能把这一步声称为全部 Gmail／Microsoft 也已互通。
不自动迁移现有邮箱密码、不重置现有买家查询码、不删除邮箱记录。
若要连同现有邮箱全部合并，需要先明确提供商兼容、查询码冲突和历史数据迁移规则，再单独实施。

## 5. 专用对接权限与接口约定

现有 ID 邮箱管理使用管理员角色校验；现有 Vendure 管理操作要求 `Permission.SuperAdmin`。
当前没有可直接使用的跨项目邮箱管理授权，不应给 ID 系统存放 Vendure 超级管理员登录凭据。

建议增加服务端专用邮箱对接身份：

- 权限仅限明确列出的邮箱管理动作；不能调用订单、商品、支付、用户管理等接口。
- 请求先通过 ID 现有管理员校验，再由 ID 后端调用 Vendure；浏览器不能获得服务端凭据。
- 服务间请求校验签名、时效、重放和调用方；具体配置项在实施时新增，并只在示例配置中放占位值。
- 仅接受预先配置的目标服务地址；失败时返回明确的连接错误，不伪造成功。
- 审计关联 ID 操作人、请求编号、Vendure 记录 ID、动作和结果；不得包含密码、查询码、验证码或邮件内容。
- 写入超时不自动重试。先判定结果，再允许人工重试；需为创建和重置等动作设计幂等处理。
- Vendure 邮箱插件已采用共享数据查询；授权前必须明确专用身份可以管理这套共享邮箱池，不能误称已有店铺隔离。

以下均是拟实现的契约，不是现有能力：

| 项目       | 执行约定                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 接口形式   | ID 暴露本系统业务接口；Vendure 增加版本化、固定动作的邮箱适配入口，复用现有邮箱服务。禁止接收浏览器传来的任意 GraphQL 文本                          |
| 身份范围   | ID 现有管理员可以通过专用身份管理本期共享邮箱池；普通用户仅能凭查询码使用公开查询。现有 Vendure 本站管理仍要求原权限                                |
| 签名       | 服务端签名绑定请求方法、固定路径、请求体摘要、操作编号、时间和来源身份；密钥只在后端配置，通过恒定时间比较验证                                      |
| 输入／输出 | 固定字段白名单、长度与枚举校验；只回传界面需要的字段，应用专用密码只写不回显                                                                        |
| 列表       | 统一服务端分页、搜索、受控排序和总数；现有返回完整数组的接口需增加兼容的分页读取，不能只把整池拉到浏览器再假分页                                    |
| 编辑冲突   | 表单携带读取时的记录版本，服务端在同一原子更新中校验；记录已被另一端修改时提示刷新并保留草稿，不静默覆盖                                            |
| 成功判定   | 写入提交并得到确定回执后才显示成功；成功后回读原记录，并刷新受影响列表及数量                                                                        |
| 超时／断线 | 写入超时显示“结果待确认”，按原操作编号查回执，禁止自动生成新编号重发；读请求可以按本项目现有策略有限重试                                            |
| 查询限流   | ID 后端把可信客户端身份绑定到已签名的请求；Vendure 仅在签名验证后使用该身份限流，同时限制调用方总量，不能信任任意转发头或让全部用户共用代理 IP 限额 |
| 错误反馈   | 区分未配置、未授权、冲突、频率限制、网络故障与待确认结果；用户界面映射中文，不显示内部异常、凭据或邮件正文                                          |
| 审计范围   | 将审计和并发约束放在共用操作服务中，让 Vendure 本站与 ID 对接操作都覆盖；ID 记录来源与关联编号，Vendure 记录权威操作结果                            |

现有 `updateIcloudRecord` 已有服务端字段比较，可以继续复用。
它不能单独解决用户打开表单后很久才提交的陈旧编辑，必须补上“表单读取版本到提交”的校验，且两端遵循同一契约。

### 数据库变更预案

ID 不新增 Vendure 邮箱副本表。预计 Vendure 需要一张受限操作回执表，承载幂等与操作追溯；
这是拟议数据库变更，不是已经批准或实施的 migration。
接口阶段先核对 Vendure 现有持久化审计能力能否完整承载，若可以安全复用则不新增；若不能则提交准确实体与迁移清单。

回执只保存调用方、操作编号、动作、目标记录 ID、带密钥的请求摘要、执行状态和时间等元数据。
禁止保存请求正文、应用专用密码、查询码、验证码或邮件内容；重试需要展示记录时，重新经过权限校验读取当前记录。
操作编号按调用方唯一，同编号不同请求内容拒绝执行。
回执与业务写入必须使用同一事务；测试连接／收信等外部动作采用明确的任务状态，不能套用数据库事务保证外部动作只执行一次。
跨进程重启仍能核查创建／换码结果；回执过期后拒绝自动重放，不把记录清理解释为“从未执行”。
迁移仅在 Vendure 项目新增，保留现有表与数据，验证升级和旧版本代码兼容。

权限、数据库或构建配置若需变更，在实施前按用户本次提供的 AGENTS.md 规则核对对应授权，
用本方案的具体范围一次说明，不在同一授权范围内反复询问。本次不创建真实凭据或外部权限。

## 6. 数据保留与展示差异

ID 现有邮箱按请求读 IMAP，邮件内容不写数据库；Vendure 现有插件自动收信并保存邮件记录。
接入后，Vendure 来源邮件继续遵循其服务端保留策略，ID 不再保存副本。
页面必须按数据来源准确说明，不能继续把 Vendure 查询结果标为“服务器不保存邮件”。
ID 原有邮箱流程仍只展示纯文本；复用的 Vendure 查询页需要独立验证邮件内容隔离、远程资源与脚本限制。

## 11. 原发布顺序与回退方案（历史规划）

此节保留原发布思路供回溯。ID 仓库的实际发布结果见第 0 节；Vendure 跨仓库待办仍需独立执行其发布流程。

1. 重新核对两仓库实际主线、生产运行版本和受影响变更；相关配置项只交付名称及占位说明。
2. 先发布向后兼容的 Vendure 对接服务及必要增量 migration，保持原站功能可用；核对接口版本和健康状态。
3. 配置 ID 后端的固定服务地址与专用身份，先做受限连通和权限验收，再发布 ID 接口与页面。
4. 核对买家查询页面、脚本和 API 的兼容版本；检查两站回读及用户授权的专用验收邮箱。
5. 分别报告提交／CI、发布版本、服务健康、浏览器功能和真实邮箱结果；全部相关门槛满足后才报告接通上线。

ID 端验收失败：关闭新增中继入口或回退 ID 版本，原 ID 邮箱功能继续服务；保留已写入 Vendure 的邮箱数据。
Vendure 端异常：撤销或停用专用对接身份，按其发布流程回退兼容代码；ID 显示服务不可用，不能回退为本地副本写入。
不通过删除新增邮箱、恢复整库或反向删除 migration 来撤销跨系统已成功的业务操作。
回退前先完成待确认操作的回执核查，避免回退后重新提交造成重复变更。
