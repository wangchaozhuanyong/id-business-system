## 真实备份隔离恢复

- 选定对象：`mysql/daily/id-business-v2-20260912T170224Z.sql.gz`。
- S3 大小：13,177,614 字节，校验远端 SHA-256 并验证 gzip。
- 转储只在内存中处理；本机临时 MySQL 使用 `--network none` 和 tmpfs 数据目录，未下载持久化的原始数据库备份。
- 从原始转储独立解析所有 INSERT 行，对每张表的全部行值生成排序后的 SHA-256 集合摘要；导入后再次导出并比较。72/72 张表的行数、主键所在行及全部字段值一致，合计 162,842 行。
- 72 张表 `CHECK TABLE` 全部通过；25 个 migration 完成，153 条外键关系孤儿记录为 0，38 项业务数据规则异常为 0。
- 转储规范化前后行值摘要相同，确认规则没有改写数据内容。

备份导入后还需恢复数据库运行前置条件：当前业务库 dump 不包含存储函数，也不包含 MySQL 服务身份；48 个触发器的 DEFINER 依赖 `id_business_migrator@%`。这两项不能由 `CHECK TABLE` 判断。

隔离演练通过项目现有迁移定义重建巡检函数，创建禁止登录的临时迁移服务身份并赋予隔离库权限；随后执行未经替换的 38 项规则、检查触发器身份、事务内普通写入与回滚、审计修改拒绝，并再次比较全部业务行值。最终未解析的触发器身份数为 0，38 项原始规则全部通过，普通写入回滚成功，审计修改被拒绝，72 张表行值仍与备份一致。该演练不创建或改变生产身份。

事故恢复必须在接入应用之前按恢复环境配置建立服务身份及最小权限、恢复巡检函数并验证 DEFINER；仅运行 `prisma migrate deploy` 无法重放备份中已标记完成的函数迁移。登录、应用密钥、真实权限和浏览器业务验收仍是独立的上线步骤。

本次证明恢复数据等于所选备份。备份产生时没有独立保存的生产全表基线，不能据此倒推该历史时点的生产数据与备份绝对一致；备份之后新增的数据也不在该恢复点中。
