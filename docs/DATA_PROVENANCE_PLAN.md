# 数据出处与操作人员规划

日期：2026-11-04。项目：ID 业务管理系统。范围：新版独立设计原型与后续正式开发契约；不改变线上系统。

## 1. 本次问题及执行边界

客户数据表缺少客户标签、历史开通业务、录入人，根因是**原型迁移遗漏**，并非老版本不具备这些功能。当前正式源码的客户列表已有标签、历史开通业务和 `createdBy`；客户仓储创建时记录 `createdByUserId`、`updatedByUserId`，修改时更新后者。旧列表将创建人员标作“操作人”，新设计改用更明确的“录入人”。原型此前的客户列表、新增、编辑和详情均遗漏了这些资料，不能只增加一个空表头便视为修复。

正式源码依据：

- `apps/admin/src/v2/features/customers/components/V2CustomersList.vue`
- `apps/admin/src/v2/features/customers/components/V2CustomerHistoryServices.vue`
- `apps/api/src/id-business-v2/customers/persistence/id-business-v2-customer.repository.ts`
- `apps/api/src/id-business-v2/customers/id-business-v2-customer-presentation.ts`

本轮原型范围：补客户标签、QQ、历史业务展示与出处，以及客户／租户录入和修改人员；补邮箱／账号主档录入人与最近操作人；补订单创建和修改人员的身份信息。具体代码、用例和页面是否通过，以本轮实际验收记录为准。本文件的“本轮”列表示明确交付范围，不替代验证回执。

其他资源、任务、配置与事件的缺口在下表登记，仍待逐项开发。没有新增正式接口、数据库字段或迁移；原型内存资料不证明服务端身份、事务、持久化或审计已接入。新版继续独立开发与测试，用户确认后再安排替换线上。

## 2. 人员字段语义

| 显示名称                         | 记录含义                                   | 更新规则                                                 |
| -------------------------------- | ------------------------------------------ | -------------------------------------------------------- |
| 录入人／创建人                   | 首次创建这条主档或批次的身份               | 创建成功时写入；编辑、恢复、续费、退款均不覆盖           |
| 录入时间／创建时间               | 该条记录进入本系统的时间                   | 创建后固定；与账号注册时间、实际开通时间分开             |
| 最近修改人、修改时间             | 最近一次成功修改主档资料的身份与时间       | 仅资料写入成功后更新；查看、搜索、切页、校验失败不更新   |
| 最近操作人、操作时间             | 最近一次成功业务事件的执行或登记身份与时间 | 提取、归还、状态变化、修改等成功事件更新；不替代完整历史 |
| 提取人、归还登记人、退款登记人等 | 某一次独立事件的登记身份                   | 随事件保存，不被后续事件覆盖；更正另记事件               |
| 发起人                           | 发起充值、续费或批量处理请求的身份         | 与执行器、人工接管人员分开保存                           |
| 实际收付款人                     | 已有证据明确的实际资金操作人员             | 不以登记人自动推断；未登记时显示未记录                   |
| 租户、归属人、认证人、内容所有者 | 业务关系或内容归属                         | 独立业务字段，不能充当录入人或修改人                     |

例如，甲录入账号，乙更正电话，丙提取：录入人仍为甲，最近修改人为乙，最近操作人为丙，提取记录也写丙。不能只用一个含义不明的“操作人”覆盖三种事实。

每个人员身份保存稳定人员 ID 与当时姓名快照；显示姓名，详情可定位人员编号。停用员工后保留原 ID、姓名快照与历史记录，不改成当前管理员。姓名变更不重写历史事件。无证据的历史记录显示“历史未记录”，不得默认填为当前登录人。

身份由服务会话或可信执行上下文取得，不提供可任意修改的表单输入；浏览器传入的人员 ID、姓名不能成为正式系统的权威来源。系统自动任务应记录系统身份、来源入口、任务编号，以及能够证明的发起人；公开兑换或 Vendure 请求不能伪装成后台管理员。

批量导入记录导入人和批次编号，每条新主档继承该批次的创建出处；如果后续允许更新已存在资料，保留原录入人，仅新增修改事件和导入关联。当前导入不得借此默许覆盖旧资料。

## 4. 客户历史业务与模块边界

客户标签由新增和编辑保存，列表、详情、搜索同步读取。每个标签项目可分别添加或移除，不使用拥挤的多行文本代替标签编辑。QQ 与其他联系方式分别成列，不合并到姓名或备注。

本轮历史开通业务按订单明确的客户编号汇总，展示业务名称、次数、首次及最近开通时间，并可查看对应订单。不能仅凭相同邮箱、电话或名称猜测客户关联。本轮仅统计已登记开通时间且不在未来、已有确认代付或历史付款证据的关联订单；退款或撤单不抹去已发生的历史。正式切片仍须核验真实开通结果，登记订单或模拟付款不代表外部业务成功。

老系统导入的历史业务后续采用独立来源标注，保留来源记录编号、导入批次及原统计期间，避免与新版订单重复累计。该历史导入能力尚未实现，不能将演示文字当成已经导入的真实历史。

邮箱管理、账号管理、订单管理继续独立。客户历史业务的聚合不要求订单邮箱在账号库存或邮箱库存中存在；成品交付选择库存只是已有便捷操作，不因此建立全部订单邮箱的强制外键关系。

## 5. 展示、接口与迁移

- 列表中录入人、录入时间、最近修改人／操作人、对应时间各用独立列，不把多项信息堆在同一单元格。默认列和列设置都提供清晰中文名称；列过多在表格内部滚动，固定关键列及操作列。
- 详情完整展示出处、稳定人员编号、业务来源及历史记录；不能仅在后台日志中存在而让业务人员无法查看。搜索、筛选按实际任务增加录入人或操作人入口，不能将当前用户当作固定过滤条件。
- 人员字段作为正式读取契约的只读元数据，创建／修改接口不接受可覆写的身份字段。服务端从鉴权会话、任务发起记录和执行上下文写入，事务成功后同步主档元数据与独立审计事件。
- 先复用已有模型和字段，缺少能力再提出增量 Prisma migration。不得修改纯净基线或重写旧迁移；历史人员只按有证据的旧字段、事件或批次回填，无法核验者保持未知并出具数量。
- 数据结构与鉴权、审计接入在后续正式切片单独确认和验收。本轮不运行数据库迁移、不写生产数据、不替换线上。
- 所有展示时间遵守北京时间。时区显示调整不改变原始事件先后和数据库时间含义。

## 6. 验收清单

1. 客户新增、编辑、列表、详情、搜索均可回读标签、QQ、业务历史；字段在列设置中可发现，切页返回保留输入。
2. 甲创建、乙修改、丙提取后，录入人保持甲，最近修改人是乙，最近操作人是丙，独立提取事件记录丙；订单和客户不会因查看而改变人员。
3. 表单伪造人员字段无效；正式接口不能借此冒用其他用户。失败、取消、重复提交、版本冲突不更新人员和时间，也不清除未提交草稿。
4. 批量导入各成功主档与批次有同一真实导入人和批次出处；拒绝行不产生虚假主档或创建记录。再次编辑不改变创建者。
5. 无历史证据的人员显示“历史未记录”；更换登录身份、员工改名或停用后，已有创建人与事件快照不丢失、不转移。
6. 自动任务、公开兑换、Vendure 能分辨来源、发起人、执行器与人工接管人；订单生成只执行一次，不将系统任务伪装为人工录入。
7. 注册更正、逐项归还、退款、余额实际回款和付租登记各有对应事件人员；操作不能顺便抹掉真实付款、注册或后续订单。
8. 客户历史业务按客户编号正确计数和首末时间，未知客户不按邮箱猜测归并；旧导入历史与新订单来源可区分、不会重复累计。
9. 桌面、窄屏、深浅主题、长姓名和未知人员正常显示；每字段独立成列，列设置、分页首末页与空状态无裁切和页面横向溢出。
10. 原型验证、正式类型／接口／迁移测试和真实页面验收分别记录结果；本地演示不作为正式持久化或上线证明。
