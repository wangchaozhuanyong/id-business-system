# 原生结算识别与填表后核价修复

任务范围：`V2-AUTO-RECHARGE-NATIVE-CHECKOUT-20261016`。

## 已核实的问题

原任务 `4553fd1c-290e-48ee-84cd-662a42e4efb1` 在本机和服务器均为
`checkout_unknown_write`、`checkout_create`、一次结算请求、零次付款请求。
官网实际已打开原生 `oaics_` 结算页；记录回传成功，问题发生在连接器识别请求和接收结算响应的步骤。
未保留原请求正文，因此不能把具体原因断言为某个字段改名。

只读读取原结算，确认当前官网返回 `custom_checkout_session`、`plan_name`、
`checkout_state.id`、`checkout_state.total.total.minorUnitsAmount` 和
`checkout_state.taxAmounts`。原单状态为 open/unpaid。
初始 PHP 1,100 是银行卡及完整账单资料填写前的参考价，不是最终应付或已扣款证据。

## 执行链路

1. 直接解析 CDP 提供的 JSON；正文不可用时保留唯一原请求并等待原响应。
   只有原请求账号、官网响应套餐、结算编号和原生状态均核实后才接续；明确错套餐、错账号和重复建单仍停止。
2. 对历史未识别原单，仅在服务端核实同一操作人、账号、套餐、原窗口和未付款记录后，
   授予原窗口只读发现资格。新任务不得重建结算，未知付款、已消耗确认或付款记录仍拒绝。
   原窗口缺失、歧义或核验失败时保留现场和旧记录，不自动关闭、换代理或重建。
3. 填写银行卡和完整账单字段并提交控件变更。街道自动补全改写定位属性时，使用正常离焦，
   不继续用失效的定位器操作。
4. 必须取得填表后更新的官网报价；原生结算还必须匹配完整账单地址及姓名的内存指纹。
   新报价请求立即使旧报价失效，迟到的旧响应不能覆盖新金额。初始化报价不能授予付款确认。
5. 展示最终今日应付、税和月续费后，沿用原有单次人工确认。
   确认后再次核对银行卡、账单、账号、原单和报价；金额变化停止付款。
6. 观察原生确认及其关联的 Stripe 原回执，先记录唯一请求，再接受严格金额和币种一致的成功证据。
   client secret 只在内存提取关联标识，不能证明付款成功，也不回传或保存。
