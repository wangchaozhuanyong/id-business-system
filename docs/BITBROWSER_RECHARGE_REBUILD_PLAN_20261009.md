# 自动充值改为比特浏览器执行：重构方案

日期：2026-10-09。状态：**方案已获授权并实施；本地验证记录见 `docs/BITBROWSER_RECHARGE_REBUILD_RESULT_20261009.md`，尚未提交、推送或发布。**

## 1. 本轮决定

自动充值统一在操作者电脑的比特浏览器中执行，移除页面上的“服务器充值”路径。网站继续管理账号、银行卡、订单、订阅和审计；官网登录、读取套餐、填写付款资料及单次付款由本机执行。

上一轮服务器充值修复、原生七服务发布及测试安排暂停。现有 PR #366 保留，未合并、未部署；本方案不继续该发布。不要创建或使用测试服务器，不使用移动代理，不进行真实充值测试。Docker 保留。

## 2. 已核实的问题

只读依据是当前远端 main `218d9829fb719810c91ecce17f62c4950548190d` 中的充值实现；本机主目录存在其他开发改动，不用主目录混合内容覆盖线上源码。以下是代码能力核实，不代表这次真实充值成功。

- 已有“本机充值”通过本机连接器控制比特浏览器，支持登录、核价、填写付款资料及单次付款。可以复用，不能只把服务器模式改一个标题。
- “仅登录窗口”已有网页直连比特接口的实现，但主动禁止付款写入，当前不是完整直连充值。
- “账号密码”中的“选择账号”会直接切到 `saved` 模式；“已保存账号”实际仍使用账号密码登录，是资料来源，独立展示为第三种登录方式造成重复。
- 现有升级证据规则将来源套餐限定为 Plus、目标限定为 Pro。Go→Plus 需要同时扩展本机流程、后端证据验证、付款结果和账务关联。
- 本机充值使用一次性地址规则，且连接器有固定地址限制；同账号再次升级不能照搬这套限制。应复用现有可用地址校验，读取用户实际账单地址。
- 本机连接器的充值与注册共用任务注册表，并修改进程内共享模块。不能通过开放两个线程实现并行隔离。
- 本机付款回调核价后直接允许继续，尚未完整接入“等待人工确认”的机制；本次必须补齐，不能把原服务器模式的确认开关当作本机已经有效。

## 3. 页面与登录方式

主操作统一为“比特浏览器充值”，主按钮为“在比特浏览器执行”。“仅登录账号”作为辅助操作保留，不继续与三种充值模式并列。

登录只保留两个选项：

| 登录方式  | 用户操作                       | 系统行为                                                                |
| --------- | ------------------------------ | ----------------------------------------------------------------------- |
| 授权 JSON | 粘贴或导入自己的授权 JSON      | 验证授权，在比特窗口核对真实账号；可与已有账号记录关联                  |
| 账号密码  | 从“ChatGPT 账号”资料库选择账号 | 受控读取该账号已保存的密码；需要验证时使用该账号既有 2FA 或提示人工处理 |

移除“已保存账号”独立选项，保留账号库和全部已有账号资料。账号没有密码时显示“请先补充登录密码”，通过现有账号编辑入口处理。页面无需让用户为了选择账号反复切换登录方式。

银行卡、持卡人、账单地址、目标套餐、付款币种与上限沿用现有资料管理。安全码和单次付款确认仅用于当前操作，按现有草稿规则不保留。

执行状态明确展示：核实账号、当前套餐、目标套餐、本次操作、官网应付金额、下一期费用、执行窗口、付款结果、套餐结果。读取中与无法核实状态不能显示为开通成功。

## 4. 同一账号连续开通与升级

每次开始都先在官网重新核实账号和当前有效套餐。本系统的历史成功记录用于关联与展示，不作为当前官网套餐的唯一依据。

| 官网当前状态             | 目标                      | 计划中的处理                                         |
| ------------------------ | ------------------------- | ---------------------------------------------------- |
| Free                     | Go / Plus / 可用 Pro 档位 | 官网提供开通入口时显示“开通”                         |
| Go                       | Plus                      | 官网提供该账号的升级入口和报价时显示“Go → Plus 升级” |
| Plus                     | 可用 Pro 档位             | 官网提供升级入口和报价时显示“Plus → Pro 升级”        |
| 已是目标套餐             | 相同套餐                  | 显示“已开通”，不重复提交付款                         |
| 套餐、渠道或报价无法确认 | 任意目标                  | 保留窗口，展示实际阻塞原因，不另开重复订阅           |

Go→Plus 的目标是支持，但不能仅按套餐名称的等级推断官网一定允许立即升级。已有订阅可能受购买渠道、周期和账户实际可用入口限制；官网没有入口时，应明确说明当前不能直接升级。

例如：先为账号 A 开通 Go，付款和官网 Go 状态均核实后记录第一笔结果；再次选择账号 A 和 Plus，重新读取官网，若支持则展示“当前 Go，本次升级 Plus”。官网返回的本次应付、折抵信息（有则展示）、后续费用与生效时间分别显示，不能把整月套餐价格当成必然补差金额。

已有订阅继续使用官网实际币种。代理国家、账单地址或页面预选币种不能被当作官网币种证明；与用户锁定币种不符时停在付款前。官方说明见 [OpenAI 多币种账单](https://help.openai.com/en/articles/10421635-multicurrency-billing)。

成功后可提供“继续为此账号升级”操作：保留账号选择和已有非敏感资料，重新获取套餐与报价，产生新的任务和单次付款确认。不能自动重复利用上一笔授权、安全码或待确认付款。

## 5. 执行方式

推荐沿用已有本机连接器，整理成一键启动的“本机充值助手”。它运行在用户电脑，调用比特本地接口和已有浏览器内核；不启动服务器浏览器，不需要 Docker，也不再额外下载另一套浏览器内核。

本机安装入口目前复用整个 Worker 依赖包，包含服务器浏览器依赖。重构时拆出只用于控制既有比特窗口的最小依赖清单，沿用现有版本，注册依赖另行保留；不把 Camoufox 等无关浏览器依赖安装到充值助手。具体安装包与依赖变化在实施清单中列明。

流程：

```mermaid
flowchart LR
    A[网站填写资料] --> B[本机充值助手]
    B --> C[电脑上的比特浏览器]
    C --> D[核实账号和当前套餐]
    D --> E[开通或升级与官网报价]
    E --> F[付款前确认]
    F --> G[单次付款与官网结果核实]
    G --> H[回写同一账号的订单和订阅]
```

服务器保留业务记录、受控取密、权限、任务凭据及审计，不登录 ChatGPT 或代理执行付款。网站将当前任务交给本机；本机网络与比特接口的必要授权失败时显示原因，不自动回退到服务器充值。

充值助手与注册执行器使用独立进程、任务队列和生命周期。窗口按业务角色及账号归属核对；账号再次升级可在身份核实后复用所属窗口，窗口失效则提示重新登录。不能误用其他账号、注册任务或操作者手工窗口。窗口名称自动生成并允许修改，不作为账号身份依据。

比特官方支持本地 API 打开／配置窗口，`/browser/open` 返回自动化连接地址：[本地服务指南](https://doc.bitbrowser.net/zh/api-jie-kou-wen-dang/ben-di-fu-wu-zhi-nan)、[浏览器接口](https://doc.bitbrowser.net/zh/api-jie-kou-wen-dang/liu-lan-qi-jie-kou)。首次仍需安装、登录比特并允许本机接口访问。独立安装包不是本轮已交付内容。

| `RechargeServerProxySettings.vue`、`RechargeServerPaymentControl.vue` 及服务器专属设置逻辑 | 从新充值入口退役，确认没有共享引用后删除                                             |

| `recharge-local.service.ts`、本机校验、`bitbrowser_connector.py`                           | 保留并收敛为唯一充值执行路径；修复地址复用与注册隔离                                 |
| `plans.py`、`subscription_upgrade.py`、本机支付流程、`recharge-upgrade-protocol.ts`        | 扩展 Go→Plus 等经官网证明可执行的升级；复用同一报价、付款和成功证明流程              |
| `recharge.service.ts`、订单与账号入账服务                                                  | 先分离共有账务／回执职责；本机服务还引用它们，不能整份删除                           |
| 原注册 Worker、邮件验证、账号库、银行卡、代理目录、账务、历史任务与迁移                    | 保留业务能力及资料；不因移除服务器充值一起删除                                       |
| 服务器专属浏览器容器、Camoufox 启动和发布配置                                              | 先核实注册引用、运行任务与回滚依赖，随后另列精确退役清单；本轮不停止服务、不删除资源 |

本次重构不把服务器执行器搬到本机继续维持两条充值路线，也不重写已有的全部账务。浏览器执行适配、开通／升级、付款控制和成功核实分别收敛，复用已经正确的共有逻辑。

## 7. 付款与结果保护

- 将付款前人工确认完整补入本机路径，保留锁定币种、最高付款额、真实账号匹配及单次请求限制。当前本机的自动放行回调必须替换为真正等待用户确认的协议，不能仅显示开关。
- 开通／升级须绑定当前账号、目标套餐和当前官网报价，确认后报价变化即失效。
- 请求已提交但结果不明时，只核对原付款与原订阅；不自动再次扣款。
- 3DS 和真人验证在所属比特窗口人工处理，不能绕过；关闭窗口、助手掉线和网页重开都有明确恢复提示。
- 付款成功与套餐生效分别核实；两项证明闭合后才记成功并更新对应账号。旧 Go 付款历史保留，升级产生关联该账号的新记录，不创建另一份重复账号。
- JSON、密码、接口密钥和安全码不进入诊断日志；秘密仅通过现有授权通道在必要内存中使用，不在新助手另存明文凭据。

## 8. 实施顺序与验收

1. 以执行时最新 main 建立本任务隔离候选，冻结注册与充值共有引用；仅修改本方案范围。
2. 简化页面、合并登录来源、接入比特连接与独立充值进程，先使账号核实和套餐读取闭合。
3. 打通 Free 开通、Go→Plus、Plus→可用 Pro；扩展 API 验证与账务关联，同步处理地址复用。
4. 用合成账号／报价验证单次付款、未知结果、断连、账号切换和再次升级；按项目要求执行类型、单测、构建、七项 UI 规则及实际页面验收。
5. 完成当前版本的准确发布清单与必需门禁后，按新的授权发布。真实账号／代理／付款验收仍待用户恢复测试授权。
6. 新路径验收完成后再删除已无引用的服务器充值代码；生产服务与恢复材料采用独立退役清单，保留全部业务数据与当前迁移。

必须覆盖：JSON 与账号库密码两方式、首次开通、同账号 Go→Plus、已是目标套餐、2FA、3DS、报价变更、回调失败、付款结果不明、刷新恢复、账号错配、注册仍在运行、深浅主题及窄屏。

方案阶段只读核实了当前路径和重复入口。用户随后授权实施，候选代码和离线证据位于本项目隔离工作区；没有调用真实比特接口、读取真实账号凭据、提取代理 IP、启动真实充值或提交付款。实施复用了既有任务结果关联所属窗口，没有新增数据库表、字段或 migration。源码收缩仅涉及已退役的充值专属入口，未停止生产服务、删除业务资料或卸载 Docker。
