# 线上代充：Pro 500 与套餐升级修复方案

日期：2026-10-15。状态：用户已批准实施，代码与本地验证结果见 `ONLINE_RECHARGE_UPGRADE_PRO500_IMPLEMENTATION_20261015.md`；未发布或真实付款。

## 目标与边界

在公司管理台内完成首次开通及已有订阅升级，准确区分 Plus、Pro 100、Pro 200、Pro 500。
正常任务沿用一次提交后自动执行的体验；身份、档位、金额或原单结果不明确时暂停并显示具体原因。
本轮只修改线上代充模块、该模块专属数据库迁移与必要检查，不修改原比特自动充值、代理业务、财务历史或其他窗口源码。
以已上线的 `20a8a9afede46a1c8e1c6d0163e315e96c4d57c7` 为业务基线，实施前核实实际线上版本变化。

官方公开价格提供 100／200／500 美元三个 Pro 档位；公开价格不能代替账号实际结算报价，
也不能用来猜测内部套餐 ID、地区价格、税款、折抵或订阅返回值。
来源：<https://learn.chatgpt.com/docs/pricing>。

## 已确认的问题

- 前端、API、数据库套餐枚举及执行器目前只有 `plus`、`pro_5x`、`pro_20x`。
- `pricing-checkout.js` 点击套餐后只等 `/checkout/` 跳转，无法完成原地“确认套餐变更”弹窗。
- 常规付款要求新卡输入，没有完整的已保存付款方式选择与归属核对。
- 当前通用 Pro 识别不足以区分全部具体档位；不能据此判定 Pro 500 成功。
- 未知套餐映射存在回落 Plus 的代码路径，新增档位时必须改为明确拒绝未知值。
- 数据库使用真实 `OnlineRechargePlan` 枚举，Pro 500 需要专属新增迁移，不能只增加下拉选项。

## 1. 先核实官方对应关系

通过已登录账号的只读套餐页面和实际订阅资料核实：

- 每档的可见名称、选择值、创建付款页所需标识，以及订阅返回中能证明准确档位的字段。
- Plus 到各档 Pro，以及低档 Pro 到高档 Pro 的页面落点与变更生效方式。
- 有折抵、无折抵、已有保存卡和新卡付款各自的页面结构。

不根据金额猜套餐 ID，不把“5 倍／20 倍”直接改名后视为完成适配。
若某档的创建参数不能被可靠验证，先显示不可用及原因，不回落其他套餐。
本步骤不点击最终付款或升级确认。

## 2. 贯通套餐与兼容旧资料

- 建立模块内一致的套餐定义，贯通套餐选择、兑换码生成／导入／验证、筛选、任务、账单、配置和执行器。
- 新增内部 Pro 500 标识；保留原 `pro_5x`／`pro_20x` 的历史语义与旧兑换码，不批量改写历史记录。
- 当前 Pro 100／200 映射核实后再统一显示清楚的档位名称；未能映射的旧码显示明确原因。
- 新增一份 migration，只扩展兑换码、任务、账单三处套餐枚举；不删除枚举、重建业务表或修改纯净基线。
- 档位、旧套餐、官网报价和执行证据优先复用现有任务 payload／result JSON，金额继续用 Decimal。
- 优先复用现有接口，不新增匿名入口、依赖或环境变量。

## 3. 自动判定首次开通或升级

| 当前账号                     | 目标                    | 处理                                     |
| ---------------------------- | ----------------------- | ---------------------------------------- |
| 免费版                       | Plus／任一已验证 Pro 档 | 首次开通                                 |
| Plus                         | Pro 100／200／500       | 升级                                     |
| Pro 100                      | Pro 200／500            | 升级                                     |
| Pro 200                      | Pro 500                 | 升级                                     |
| 与目标相同                   | 同档                    | 停止，提示已是目标套餐，不记本次充值成功 |
| 高档到低档                   | 降档                    | 本轮不自动执行，明确提示                 |
| 当前档位、账号或订阅状态不明 | 任意                    | 停止，不能猜测后付款                     |

账号仍有付款或续费待核对任务时，继续阻止创建新的变更任务。
Go 等其他来源套餐本轮不顺带扩展；未纳入矩阵的来源明确停止。

## 4. 补齐原地升级与实际付款方式

- 按实际页面区分新卡 Checkout 与原地套餐变更弹窗，不要求所有升级都跳转 URL。
- 升级弹窗内核实目标档位、币种、周期价格、官网列出的折抵／税费及“今天应付”。
- 折抵由官网报价决定；系统不按美元目录价手算差额，不把月费当本次应付。
- 已保存卡只能在能够证明它与本次允许使用的卡一致时选用；尾号不唯一、默认选中其他卡时不能直接扣款。
- 不能核实保存卡时，使用明确可识别的新卡入口；没有该入口则停止并提示，不静默更换付款方式。
- 实际使用哪张卡，就记录哪张卡；不能给官网默认卡扣款，却增加另一张卡池卡的次数。
- 官网要求验证码、3DS、CVC 或人工验证时进入对应待处理状态，原任务继续，不能新建付款。
- 升级不额外执行取消／恢复续费；实施时隔离当前成功后自动取消续费调用，保留原首次开通策略的既有范围。

## 5. 单次提交与成功判断

- 点击前记录原账号、原档位、目标档位、实际付款方式及本次官网报价；提交标记必须早于最终按钮操作。
- 将最终按钮定位限定在已核实的付款页面或升级弹窗，不扩大通用“支付”文字点击范围。
- 每次任务只提交一次。超时、“未能完成套餐变更”、响应中断等情况只核对原单和原账号，不换卡再扣。
- 成功证据区分订阅变更与扣款：同账号准确目标档位、生效状态和对应原单／实际金额必须一致。
- 只有通用“Pro”、未来待生效档位或无法对应的金额时，保持待核对；不能用原有订阅或目录价补成功账单。
- 明确零应付需按有凭证的零金额变更处理，不能标为实际扣款；未知金额不能写成 0。
- Pro 500 未证实之前不得用 Pro 200 或通用 Pro 作为成功凭据。
- 第三方通道只有在供应商明确支持具体档位和升级时才启用；否则对该组合提前提示不支持，不透传猜测的参数。

## 6. 验收顺序与通过标准

1. 定向单元与集成测试：套餐映射、旧码兼容、迁移、权限、任务幂等及金额精度。
2. 模拟页面覆盖：新卡 Checkout／保存卡升级／折抵与零应付／同档和降档拦截／保存卡不匹配／Pro 档位模糊。
3. 回归付款结果：扣款成功但弹窗报错、网络断开、租约丢失、重复点击、迟到回包；原任务不能产生第二笔付款或第二份账单。
4. 管理台页面验收：深浅主题、窄屏、加载与输入保留；运行项目要求的七项 UI 检查、相关类型检查和构建。
5. 隔离 MySQL CI 验证新增 migration 与旧数据兼容；本机不启动整套网站或数据库，不访问生产库测试。
6. 官网只读／付款前验证各目标档位和升级弹窗。实际付款需另行明确账号、目标档位、币种、金额上限和续订条款；旧 Pro 首次开通授权不用于新测试。

优先覆盖 Plus 到三个 Pro 档、Pro 100 到 200／500、Pro 200 到 500。每个未做真实业务验证的组合如实标记未验收，
不以一笔付款或模拟页面代表全部套餐已成功。
