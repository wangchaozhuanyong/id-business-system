# 自动充值失败任务与付款保护分离

任务：`V2-AUTO-RECHARGE-PAYMENT-AVAILABILITY-20261015`。用户于 2026-10-15 明确批准实施已讨论的方案。

## 行为

- 已结束任务释放执行名额；租约到期显示“执行租约已结束”。任务结束或超时均不等于银行未扣款。
- 按本次执行、原付款结果、账号付款限制三个维度展示状态。连接、登录、核价失败且没有付款请求，不新增付款限制，也不能清除同账号的旧未知付款。
- 付款限制匹配当前准备操作的账号，不以当前正在查看的历史任务代替当前账号。查看历史不会自动切换登录账号或清空付款资料；明确选择“继续同账号”时沿用既有切换流程。
- 未知付款、需要验证、已有付款凭据但订阅待生效，继续限制同账号新付款。仅登录、查询原单和其他账号仍可操作；正在运行的物理执行任务继续遵守单执行器资源保护。
- 分页只读核对本人全部执行记录，支持任务编号／窗口名称搜索，固定按创建时间和编号倒序。失败保留最后成功内容，分页、搜索和选择使用共享会话草稿；不批量清空或自动解锁未知付款。
- 原窗口丢失时先通过“仅登录”核实同一账号，然后复查原付款任务。服务端可以选择后续已有登录任务的窗口，仍须在官网核对身份；恢复时固定原订单编号，执行端只读账本也必须匹配该编号。更换窗口不授权新建结算或付款。

## 已拒付原单的受控结束

只提供明确拒付原单的处理能力，不用于付款结果未知、需要验证、已付款或升级单。

1. 原任务已结束，保留有效原订单编号、同账号同套餐的唯一持久付款记录，状态明确为拒付，确认次数为一次且没有成功付款凭据。
2. 付款结束之后已有同一账号、同一操作人的免费版官网核实记录；不能用付款前的免费版快照代替。
3. 操作人先核对银行账单，在界面明确确认没有扣款或待入账交易。无法确认时取消处理，继续保留保护。
4. 服务端在现有事务和发布 scope 内核对当前原单、归属、运行任务和持久记录；生成真实的已结束处理记录，更新原单处理标记并写审计。保留付款状态、付款次数和原付款文件，不伪造未尝试付款。
5. 新标记为 `confirmed_declined_no_charge`，复用既有 JSON 处理字段。旧拒付付款文件留存；只允许已经核实的旧结算进入新的核价流程，新结算不能继承旧的结束证明，仍需新报价和人工付款确认。其他未知付款仍会阻止新付款。

## 接口和存储

- 新增 `GET /api/id-business-v2/auto-recharge/jobs/review`：`page`、`pageSize`、`search`，仅当前操作人，最大每页 100 条；读取及补充核对均不写数据库。
- 新增 `POST /api/id-business-v2/auto-recharge/jobs/:id/resolve-declined`：明确的 `confirmNoDebit: true` 和 `verificationJobId`，沿用管理员角色、原任务归属和事务审计；重复处理返回同一处理记录。
