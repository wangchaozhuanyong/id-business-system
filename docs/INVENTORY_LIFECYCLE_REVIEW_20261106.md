# 邮箱、账号、订单与提取归还闭环核对

日期：2026-11-06。对象为最新独立站。下文保留实施前核对及确认方案，实际交付见文末。

## 核对结论

用户提出的方向可行：提取是暂时领用，实际注册或正式业务使用才消耗库存；已使用资料保留原批次证据，同时进入对应管理列表的已使用视图，不能作为未使用归还。

当前只完成部分闭环，自动识别仍有缺口：

| 环节 | 当前实现证据 | 缺口 |
| --- | --- | --- |
| 隐藏邮箱状态入口 | `frontend/apple-relay-prototype.js` 的 `useOptions`、`renderAliases()` 已有未提取、已提取、已实际使用，并与账号状态交叉筛选；4371 提供的脚本与源码一致 | 入口位于“隐藏邮箱”页内，不是最上层四个页签；需统一使用状态文案与入口。当前浏览器停在登录页，未把用户看不到按钮的具体原因认定为已查明 |
| 提取与归还 | `frontend/inventory-prototype.js` 的 `createBatch()`、`returnBlock()`、`requestReturn()`、`submitReturn()` 支持逐条结果、禁用阻止项、只归还所选未用项，并在确认时复查 | 只识别已经写入库存的使用、任务或登记关联，不会从独立账号／普通订单补查遗漏 |
| 注册成功 | 登记外部注册成功时调用 `consume()`，邮箱和原提取明细都转为已使用 | 新增账号、批量导入账号没有自动消费对应邮箱 |
| 成品订单 | `checkStockDeliveries()` 校验订单与库存使用记录共同保存，拒绝重复交付；前端 `prepareAccountSale()` 提供配套资料 | 前后端只接受原状态为 available 的账号，已经提取的 claimed 账号不能直接继续交付 |
| 普通订单 | 现行 `docs/DESIGN_SPEC.md` 第 4.1.1、4.2 节明确不按相同邮箱建立关联 | 用户这次提出了新的联动方向，需要同步替换这条旧约定，再统一实现 |
| 已使用列表 | 常规库存 `inventoryPage()` 的已使用数量及列表只包含 health=normal | 已使用后变死号或解封中会离开已使用视图；使用事实和健康状态应可同时查询 |
| 时间字段 | `createBatch()` 在提取时填了资产 `usedAt`，批次明细另有 `claimedAt` 和实际 `usedAt` | 应区分提取时间、业务发生时间、识别时间，不能把提取时间称作实际使用时间 |

## 建议统一规则

| 发生的业务 | 邮箱状态 | 账号状态 | 原提取批次 |
| --- | --- | --- | --- |
| 成功提取 | 已提取待使用 | 提取账号时同样为已提取待使用 | 新增待使用明细，保留领取人和用途 |
| 账号正式录入／批量导入成功，唯一匹配到已提取的来源邮箱 | 邮箱已使用，关联该账号 | 新账号仍为未使用库存，不能因邮箱用过就判账号已交付 | 对应邮箱明细变已使用 |
| 已提取邮箱作为有效订单的业务账号邮箱使用 | 邮箱已使用，关联订单 | 有同产品、可确认归属的已提取账号时，分别更新该账号 | 分别更新匹配的当前领取明细 |
| 已提取账号被正式交付订单使用 | 该账号已有明确来源邮箱时补齐关联 | 账号已使用，关联订单 | 对应账号明细变已使用 |
| 注册／执行结果未知或仍在进行 | 保留领取或任务占用，显示待核对，不允许归还 | 同左 | 保留待处理原因，不虚构成功或失败 |
| 确认未使用且无在途占用 | 按归还理由恢复可用或转死号／解封中 | 同左 | 原明细标记已归还，不删除、不重开 |

“有效订单”必须指保存成功、明确使用该资源的正式业务记录。输入框中的文字、未保存草稿、导入预览、客户联系邮箱、支付 Apple ID 邮箱不作为使用依据。订单若只是排队申请、尚未执行，先保留订单占用；正式交付或使用确认才消费。如果现有录单代表对已经发生业务的登记，成功保存该正式订单即可作为触发点，不必等收款才确认资源已经用过。

## 匹配、归还与补核

1. **稳定关联。** 邮箱文本用于发现候选，保存明确的邮箱编号、账号编号、订单编号、提取批次及领取明细编号。账号匹配必须带产品类型；同邮箱 GPT 和 Claude 不能互相消费。按现有邮箱规则去首尾空格及处理大小写，不擅自删除点号或加号后缀，也不把隐藏地址与主邮箱合并。
2. **唯一且可确认才自动。** 匹配到多个来源、其他人的领取批次、业务产品与领取用途冲突、旧单发生在本轮提取之前时，列为待核对，不能任选一条使用或允许直接归还。苹果收信主邮箱、账号登录邮箱、订单目标邮箱、支付用 Apple ID 必须区分角色。
3. **三处一起更新。** 保存账号或订单时，在服务端共同完成库存状态、使用关联及当前领取明细更新。失败全部不生效，重复提交不重复消耗。页面刷新、切页和其他操作员看到相同结果。
4. **归还再次核验。** 打开归还时先核对，确认提交时再检查最新账号、订单、注册和任务证据。示例：批次十条中六条已用，只允许勾选四条未用；六条显示已使用及关联依据。确认期间有一条新增使用，应刷新资格并要求重新确认可归还条目，不能沿用旧选择，也不静默少还。
5. **保留历史、统一视图。** 已使用资料出现在管理页“已使用”中，同时保留在原批次内；这应是同一条主档的不同视图，不复制成独立数据。健康状态单独筛选，因此“已使用＋死号”也能查到。批次显示原数量、待使用、已使用、已归还，便于核对总数。
6. **历史补核和录入顺序。** 新账号／订单保存触发识别；归还前检查兜底；已有历史资料提供可复核的匹配清单。先录账号后补邮箱、先有订单后补账号、批量导入，都要走同一规则。未曾提取但已有确定使用证据的资料可标记已使用，但不编造历史提取批次。旧批次已归还后再提取的资料，只更新与实际业务时间及关系相符的明细。
7. **退款、撤单和更正。** 注册或交付事实发生后，退款、订单取消、记录归档不让库存自动变回未使用。真正的误关联要单独更正并保留原依据；待执行订单取消且确认从未使用时，才解除占用并允许归还。续费只追加业务历史，不再次消耗同一个账号，也不能把客户自有账号当库存交付。
8. **系统外使用。** 没有账号或订单记录的外部注册无法仅靠本机表自动知道，应保留现有“登记使用／登记注册结果”入口。不能把“没找到订单”当作一定没用过。

## 实施验收建议

逐项覆盖：邮箱→账号、邮箱→正式订单、账号→正式订单；单条和批量录入；十条用六还四；确认期间并发使用；同邮箱不同产品；客户续费与库存交付；主邮箱／隐藏邮箱／支付邮箱区分；注册失败与结果未知；先业务后补库存；归还后二次提取；重复提交；退款撤单不复活库存；已使用后死号仍可查询。检查数据库、批次和各视图一致，不能只验证页面标签变化。

## 实施结果

- 服务端通过 `server/inventory-usage.mjs` 在库存与订单保存事务中识别使用关联。账号录入可消耗来源邮箱，已确认付款的订单可消耗符合领取依据的订单目标邮箱，成品订单可交付本人已提取的账号。未确认订单暂时阻止归还，撤销未执行的订单后解除阻止。
- 归还前读取最新使用依据，提交时服务端复查。历史资料提供“核对使用关联”，明确的结果可同步。归属、时间或来源有冲突的资料保留待核对。原批次与使用历史保留。
- 隐藏邮箱页显示“库存／已提取／已使用”。已使用列表保留死号和解封中的记录。提取时间和实际使用时间分开保存。沿用原 SQLite 文档，无需数据库迁移。
- 管理员可在资料详情更正自动关联。系统保留原使用依据、批次结果、理由、操作人和时间。同一误关联不会自动生成。若无其他有效依据，则恢复原待使用状态，或在原本没有提取批次时恢复库存。正式交付及手工确认记录沿用原业务规则。
- 全量回归 338 项和浏览器检查 8 项通过。浏览器验证了隐藏邮箱筛选、部分归还、成品下单及谷歌邮箱和苹果隐藏邮箱更正。邮箱池用例已区分建池验证与买家查询，复验通过。
- 4371 已重载并核对相关页面脚本，右侧停在登录页。
