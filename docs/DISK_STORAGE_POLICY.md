## 保留和容量规则

| 内容                       | 规则                                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| 已上线服务镜像             | 保留现用及每服务一个不同的回滚版本；当前/上一版清单、全部运行或停止容器引用始终保护                  |
| 待发布内容                 | 每个模块最多一个完整候选；同模块新候选通过来源、Git 祖先和全部 ECR 身份核验后才能替代旧候选          |
| 已被替代的线上代充候选     | 仅明确登记为被替代的批次可回收；逐项核对本地 ID 和 ECR 可恢复的相同 ID                               |
| 恢复和验收依赖             | 沿用已核验的精确依赖；不能为了满足数量或容量而删除仍需要的版本                                       |
| 来源不明、混合标签和新构建 | 保留并在回执报告；最大运行号、镜像年龄或零容器引用都不能单独作为过期证明                             |
| 系统空闲                   | 目标 12 GiB；低于 10 GiB 标记不足，低于 6 GiB 标记紧急；既有发布门禁保持                             |
| 发布源码、暂存与归档       | 合计预算 4 GiB；超额登记归档事项。当前历史链必须先封存、校验恢复及修复读取路径，不能按日期直接删目录 |
| 本机数据库备份             | 沿用现有 48 份/1 GiB 默认限制及必要恢复点保护；保护集合超额时报告，不能删除恢复点来强行满足上限      |
| 系统日志                   | 预算 1 GiB，沿用系统轮换；容器日志保持现有每容器 20 MB × 10，不在本轮修改                            |

数量规则优先约束无用候选；容量预算不能覆盖业务数据和恢复保护。没有安全候选时停止并说明缺口，不使用全局 prune 或强制删除。

## 每次发布的容量管理

普通发布以及后台、代充、API/工作区、组合模块、充值流程的八种正常发布入口均接入三个步骤；历史特例及镜像复用继续使用原来的严格流程，不能假冒新 producer。

1. 构建前：先按已批准规则回收可恢复的过期镜像，再进入既有最低空间及闲置检查，避免先被 6 GiB 门槛拦下而无法回收。
2. 镜像完整推送后、服务器拉取前：核对实际源码树、质量检查、完整角色、本地展开大小及 ECR config digest，登记唯一候选。估算未在服务器存在的镜像展开大小与压缩下载临时占用，再加三份源码传输余量及 2 GiB 收尾空间；不能把仓库压缩大小当成磁盘大小。不足时在下载前停止并保留候选。
3. 正式发布和独立回读完成后：再次读取服务器实际 manifest、producer、质量检查与运行镜像，才把候选标为已发布并回收更旧版本；现用、每服务回滚、容器和恢复依赖继续优先保护。

三个步骤均使用发布锁、固定来源摘要、完整候选账本、实时保护集合和精确 ECR 恢复核验。账本变动会使旧清理计划失效；已回收的整批本地镜像不存在后才能压缩账本记录。新步骤要求维护入口已经正式安装；未安装、版本漂移或回执不确定时停止，不能当作成功跳过。

稳定规则安装后，旧人工镜像清理入口会明确拒绝，旧历史发布的两种自动镜像维护也会跳过，防止绕过新候选账本。历史特例继续沿原发布核验流程执行，镜像回收交给新的稳定维护入口。只读诊断与备份、日志等独立规则不受此镜像归属切换影响。

本轮未修改 Docker 构建配置。代充镜像的安装层和重复权限修改约占数 GB，减小它们及复用依赖层是后续构建优化项，需要按项目构建配置规则审批。

## 每日维护

独立任务名 `id-business-v2-disk-retention`，安装到稳定的 `/opt/id-business-v2/maintenance/disk-retention`，不依赖可变 `current/scripts` 路径。

每天 UTC 03:15，加最多 15 分钟随机错峰，即马来西亚时间 11:15–11:30。任务先核对批准的配置、源码、当前清单、现用/回滚/候选/依赖及云端精确恢复证明，再生成计划、删除精确引用并保存回执。发布锁被占用时本次跳过，不等待或干扰发布。

安装默认只生成计划。显式安装批准必须匹配真实安装计划摘要；当前版本、容器、目标文件或单位身份变化时拒绝安装。未知或不匹配的现有文件不覆盖。新任务启用且回读通过后，才按既有严格核验函数停用已确认的孤立旧 timer；旧单位、故障历史、数据与备份保持。旧任务状态不明时原样保留并报告。

执行前写不可变计划，逐项删除前后写独立私有回执，并同步文件与父目录；失败保留已确认删除的前缀和最后未确认动作。重做前必须回读真实结果，不能直接重复删除。配置、源码、当前版本和保护集合发生变化时停止。

目录和备份预算当前只读监测，未添加通用目录删除或数据库写入功能。历史目录归档尚未完成，不能把镜像清理和每日任务安装当作所有存储治理已经完成。

## 安装与验收

本次新增运维 Python、受审核策略、发布步骤及控制检查，不新增业务接口、表、字段、依赖或环境变量；无需数据库迁移，不启动本机 Docker 或数据库。

安装和首次清理分开留回执，须按项目授权流程执行。安装后核验源码摘要、root 权限、真实 timer 启用状态及下一次时间；清理后读取实际磁盘余量、镜像保护集合、当前清单和容器身份。只有这些完成才能报告规则已生效或空间已释放。

正式维护入口为 `.github/workflows/disk-retention-maintenance.yml`，与网站发布共用 GitHub 并发组和服务器发布锁。先核验通过 main Quality Gate 的精确来源、AWS 身份和服务器目标，再通过 SSM 按原始摘要保存专属私有暂存源码；已有未知文件不覆盖。

操作顺序为 `verify_install` 取得实际安装计划、`install` 绑定该计划摘要、`verify_cleanup` 取得实际清理计划、`cleanup` 绑定该清理摘要。首次清理不使用自动批准模式。维护入口只安装维护源码和定时器并回收已核验镜像，不切换业务版本、不执行迁移。受理回执或结果不确定时先回读原操作，不重复派发。
