# 首次自动充值实测修复

用户明确使用故意错误的银行卡资料，验收目标是自动流程能够向官网提交一次付款。银行卡不能通过支付方式验证属于预期结果，不作为自动化故障，也不能据此宣称充值成功或银行没有收到请求。Go／Plus 后续升级至 Pro 另行规划。

## 实测与修复范围

| 问题 | 根因与修复 | 验收边界 |
| --- | --- | --- |
| 免费账号已核实，但长期停在会话恢复 | 首次开通只等待付款入口所需状态，使用本轮刷新的授权目标，不以聊天输入框就绪作为付款前提 | 账号身份、会话有效性与原窗口核对仍保留 |
| 首次 Pro 最高档无法选择 | 识别官网“升级订阅”和个人套餐入口；在同一个原结账单中选择唯一目标档位，使用真实 Page 支持的 Locator 接口 | 未验证档位时停止，不猜档、不另建结账单 |
| 恢复原单后误判档位或税费 | 依据服务端实际保留的可信字段恢复首次开通判断；核对当前原单官网金额及唯一实际税额，包括 VAT 文案 | 未知、歧义、跨字段税额均停止，金额不按税率推算 |
| 已解决的历史付款记录仍挡住本次原单 | 使用已有账号级付款资格检查，保留未解决的未知付款锁，不把所有历史文件一律视为未解决付款 | 不自动解除历史锁，不重试未知付款 |
| 付款确认超时后回显初始报价 | 到期结果携带已核验的最终报价和确认阶段；外层只在没有明确报价时补充初始报价 | 五分钟确认期限、过期失效和单次授权不变 |
| 本机 hCaptcha 没有明确提示 | 本机也识别可信、可见、绑定原单的挑战，在既有预算内提示本人验证并继续观察；结束时明确保留原因 | 不自动解题，不扩展服务器输入桥或网络授权，不再次点击付款 |
| 支付方式验证失败与未知付款混在一起 | 原账号、原结账页面的精确可见失败提示转为受控诊断；官网或银行验证类型不明确时使用统一措辞 | 页面提示不生成付款成功、银行拒付或未扣款证据；金融未知状态和防重锁保留 |
