# 客户流失与订阅分析规划

2026-11-09 · 首版已在本地实现。入口为「数据管理 → 客户流失」，旧链接和网站总览可继续进入。页面复用现有客户、订单、库存使用关系和续费关联记录。

2026-11-10 用户明确修订：客户流失统计已开通过、订阅已到期且没有续费的客户。正常人工 GPT／Claude 订单已登记的订阅起止时间就是统计依据，不能因未勾选代付、实收或成本确认，或续费未填写邮箱，就整批归到「开通凭据待核对」。付款、成本等财务核对继续保留在订单里，流失统计不修改这些标记。下表按本次口径更新。

## 现状判断

保留客户级判断。客户名下只要还有一项有效订阅，就不会进流失名单。续费管理继续处理单笔到期与拒续，客户流失用于判断这个客户整体是否停止使用、值不值得跟进。改版前名单主要显示联系方式、最近业务和到期时间。

- 改版前历史抽屉把待补全记录和已确认订阅一起展示，缺有效周期的订单也可能未出现在「待核对」。现在历史条数、已确认订阅次数和待核对订单分别统计。[客户归集、流失列表和历史抽屉](../frontend/commerce-prototype.js)
- 部分自动代充同步单只有任务号、账号、套餐和开通证据，客户编号为空。可先核对任务结果和归属，归属确认后纳入该客户的画像。客户自用账号可能换号，库存账号也可能被回收后交付给另一人。[代充订单同步](../server/recharge-order-sync.mjs)
- Claude 谷歌订阅管理以账号邮箱为单位，用于查订阅账号资料。客户画像以客户为单位，归集多个产品和账号的记录。[Claude 订阅账号投影](../server/claude-google-subscriptions.mjs)

## 第一版界面

| 区域 | 显示与操作 |
| --- | --- |
| 页首 | 「已流失」「待核对」「待生效」各自显示数量。「待生效」列出曾开通过、当前没有有效服务、已登记未来订阅的客户。摘要显示已流失客户、近 7 天停止服务、待核对及待生效，并注明统计时点和来源覆盖。 |
| 筛选 | 搜索客户、联系方式、历史账号或订单号。按曾订阅的产品与套餐、停止服务距今天数、订阅次数筛选。默认最近停止服务优先，可按历史订阅次数排序。 |
| 客户行 | 客户、常用联系方式或「查看联系方式」、订阅次数、套餐分布、最近订阅、最后服务结束和距今天数。套餐较多时折叠到摘要，完整明细放在抽屉。待核对行明确写出缺少归属、周期缺失或数据冲突。 |
| 右侧「客户订阅历史」 | 显示已确认次数、最早及最近可查开通时间、套餐次数、已关联原单的续费、有效服务数和账号数。按开通时间分页显示原订单、来源、账号、产品套餐、订阅周期及当前状态，待核对记录单独标注。点击订单号核实原单，客户资料详情也可进入同一抽屉。 |
| 手机端 | 先呈现客户、套餐摘要、订阅次数和停用天数。筛选自然换行，操作和说明按共享间距规则排列，沿用共享抽屉。 |

示例：同一位客户已确认 GPT Plus 两次、Claude Max 5x 一次，摘要显示「3 次 · GPT Plus 2 次 · Claude Max 5x 1 次」。如果 Claude 还有效，他仍是有效客户。全部服务结束后，流失页展示他最近用过的套餐和已停止天数，方便决定是否优先跟进。

## 计算与数据口径

| 指标 | 规则 |
| --- | --- |
| 客户归属 | 首选客户编号。缺编号时，只在标准化的同渠道联系方式唯一指向一个客户且无冲突时归集。无法唯一匹配、多个客户共用联系方式或账号转手待确认时，进入待核对。仅有相同姓名、订阅邮箱或银行卡线索时，由人员核对原订单归属。 |
| 订阅次数 | 正常人工 GPT／Claude 订单按已登记且有效的订阅周期计算，不要求财务确认、付款凭据、金额或续费邮箱齐全。自动代充仍依据已同步的成功开通结果；Gemini／Grok 沿用明确的权益开通状态。按订单稳定编号去重，自动代充按来源和任务号去重，同一记录的补录、重试和更正计一次。撤单、失败、明确草稿不计开通，也不因其付款字段阻止客户按已有到期订阅归类。缺少或无效的订阅周期、未明归属和重复冲突继续单列待核对，不把未知周期当成已过期。 |
| 套餐分布 | 以订单保存的产品和套餐为准，已知旧名称统一显示，原值保留在明细。订阅次数按套餐分组，未知套餐单列待核对。只有明确关联的新周期才单列为已确认续费，不能用订单的「续费」业务类型推算。 |
| 有效服务 | 同一统计时点按北京时间判断，开通时间小于等于当前时刻，且当前时刻早于已确认服务结束。按有效期、确认终止或库存释放判断。拒续只影响该单提醒，部分退款和全额退款按是否实际结束服务分别核对。已真实提供过服务且后来退款或终止的记录，仍保留在历史。 |
| 流失及停止天数 | 至少有一次已经开始的有效订阅记录，名下服务都已结束、没有有效续费，且没有会改变周期判断的资料缺失时计入流失。同一客户换账号续费、购买其他仍有效的套餐或已登记未来续费，均不误判为流失。未勾选财务确认不属于阻止归类的原因。续费后来再次到期，按最后服务结束时间重新计入；到期时刻本身即为已结束。停止天数以最后一项服务的实际结束为基准，有明确提前终止事实时优先使用。仅有终止标记且缺结束时间时显示待核对，停止天数留空。未来订阅单列「待生效」。 |
| 统计覆盖 | 首版覆盖现有 GPT、Claude Pro、Claude Max 订单与已同步的代充记录。Gemini、Grok 等以实际接入为准。最早订阅、累计次数等均为本系统可查范围，记录缺失、读取失败、未关联分别显示。摘要的客户数按客户去重，待核对订单数按订单去重。 |

## 实施次序与验收

1. **首版已实现。** 导航、只读统计、筛选、订阅历史、待核对与待生效。列表、抽屉和总览共用客户统计口径。库存回收或停止复用按原订单对应的事件计算实际结束时间，未取得库存使用关系的相关订单进入待核对。首次读取显示加载或错误状态，刷新失败保留已读资料并提供重试。沿用现有可见范围，复用既有接口，无新增表、字段或迁移。
2. **核对与跟进。** 首版的待核对可跳到原订单补关联和周期。结构化的「已联系、待回复、暂不续、已回流」、负责人和下次跟进时间是后续设计。联系人回复或订单证据支持时才登记原因。跟进状态与实际有效服务分开。
3. **趋势。** 开通、结束与回流时间可核实时，再做按月净流失及套餐分布。以月初有效客户为分母，统计这批客户中当月停止全部服务且月底未恢复的人数。新增客户的当月流失单独看，金额指标等实收、退款及币种口径可核对后再纳入。

验收样例覆盖一人多产品、换号重新开通、同号转交另一客户、同一任务重复同步、订单待补全、无归属成功代充、同渠道重号、计划未生效、实际终止和部分退款。核对套餐分组数、列表客户数与首页指标一致。日期不全或数据读取失败时明确展示对应状态。实际历史覆盖需要用获准的资料抽样确认，当前规划以源码和离线合成数据为依据。
