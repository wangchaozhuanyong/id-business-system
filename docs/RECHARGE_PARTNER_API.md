# 合作方充值 API 接入说明

ID 系统为每个合作方发放独立 API 密钥和指定套餐的兑换码。MOYAO 使用同一套接口，其他网站可以从自己的服务器接入。文中的域名、兑换码和请求均为示例。

## 管理后台发放

1. 超级管理员打开「线上代充 → 充值 API 接入」，填写名称并创建合作方。复制接入资料并连同本文交给对应合作方。原始 API 密钥只在创建成功时返回一次。
2. 选择合作方、套餐和数量，从现有可用库存发码。复制该批次的 `RA-` 兑换码交给合作方。套餐支持 Plus、Pro100 和 Pro200，对外分别表示为 `plus`、`pro_5x`、`pro_20x`。同一发码提交的重试返回原批次。
3. 合作方在自己的后台或服务端配置中填写接入资料，通过服务端验码、发起充值或查进度。每家凭证只读取及使用发给本家的码和对应任务。停用凭证即时停止该凭证的新请求，已经受理的任务照常保留状态和凭据。

## 合作方服务端接口

所有接口使用 HTTPS。服务端在 `Authorization` 请求头用 `Bearer` 方式提供 API 凭证。接口返回 JSON，错误返回固定的业务错误码。下表以 `https://id.example.test/api/recharge/v1` 为 API 地址示例。

| 操作 | 方法与相对路径 | 请求 | 结果 |
| --- | --- | --- | --- |
| 验证连接 | `GET /config` | 无 | `maintenance` 为 `false` 时可受理新请求 |
| 验码 | `POST /codes/verify` | `code` | 兑换码绑定的套餐和可用状态 |
| 发起充值 | `POST /redemptions` | `code`，`Idempotency-Key` 请求头 | 充值请求编号、有效期、ID 系统授权链接 |
| 查询请求 | `GET /redemptions/{id}` | 原充值请求编号 | 套餐、状态、阶段和更新时间 |
| 按码查询 | `POST /codes/query` | `code` | 套餐、状态和最近一次允许访问的充值请求 |

以下为合作方服务端提交的示例。地址、凭证和兑换码均为占位值。

```http
POST /api/recharge/v1/redemptions HTTP/1.1
Host: id.example.test
Authorization: Bearer PARTNER_API_KEY
Content-Type: application/json
Idempotency-Key: partner-order-1042

{"code":"PARTNER_REDEMPTION_CODE"}
```

首次创建返回 `201`，恢复原请求返回 `200`。响应包含 `id`、`plan`、`status`、`stage`、`updatedAt`、`expiresAt` 和可用时的 `authorizationUrl`。把链接作为顶层浏览器导航交给客户。授权窗口为 15 分钟，客户在 ID 域名核对账号及套餐并提交，第三方按请求编号查询进度。

每笔业务使用稳定的 `Idempotency-Key`，最长 120 字符，可用字母、数字、点、下划线和连字符。同一密钥和同一兑换码重复提交取得原请求。以同一编号提交另一兑换码返回 `409`。遇到网络中断可用同一编号恢复，或按码查询。`authorizationUrl` 只在当前请求仍可授权时返回。已受理但结果未知的任务维持待核对状态。过期未受理或执行前失败且已人工批准一次重试时，可用原兑换码及新的请求编号重新发起。

| 对外状态 | 展示依据 |
| --- | --- |
| `awaiting_authorization` | ID 已创建申请，客户尚未发起执行 |
| `expired` | 授权在受理前过期 |
| `queued`、`running` | 网关原任务回执与执行阶段 |
| `succeeded` | 执行端确认已开通 |
| `failed` | 执行端有明确的失败结论 |
| `awaiting_review` | 已受理但付款或开通结果待核对 |

凭证无效返回 `401`，他方或未知的兑换码和编号统一返回 `404`，防止通过差异确认他方交易是否存在。请求超出频率返回 `429`，服务暂不可用时返回 `503`。返回字段按固定列表生成，响应禁用缓存。

## MOYAO 接入

MOYAO 在现有「GPT 自助充值」管理页填写 ID 系统发放的 HTTPS API 地址和「合作方 API 密钥」。商城接受站点地址或含 `/api/recharge/v1` 的地址，站点须位于原商城服务端允许列表中。商城服务端根据 `RA-` 码使用合作方接口，原兑换码继续用原商城服务凭证。前台验码后生成授权链接，按原兑换码查询进度。独立开发的网站使用上表中的 API 完成同样的操作。

此前 MOYAO 的固定对接已存在真实回执。切换时须保留原连接和查询方式，核对旧兑换码、失败回执和仍在处理的任务。合作方接口使用可独立识别的批次和请求编号，商城按归属和协议读取对应回执。新接口仅接受已绑定给调用方的兑换码。旧专用接口必须拒绝已分给其他合作方的兑换码。

## 正式发布与运维

- ID 的凭证、批次和授权请求优先复用现有加密业务文档与事务。应用服务鉴别合作方，服务端按兑换码及请求归属授权。账户密码、登录角色和数据库表结构沿用当前设计。
- ID 正式发布流程的 `include_recharge_partner_api` 选项在同一发布锁内更新网站与商城任务网关。两端通过私有 Unix 套接字收发请求，继续使用原队列和执行器。切换网关前核对没有待领取或运行中的任务，验证原 worker 已恢复轮询后才恢复受理。
- 主分支已合并的 0 元试用策略应继续走它自己的原生版本发布。合作方发布只接受该批次的精确构建输入，旧版充值页面制品摘要及现用原生镜像身份仍须通过原有校验。
- 先验证指定 HTTPS 域名的授权页、代理来源验证、匿名 API 拒绝、网关版本和商城旧通道，再部署 MOYAO 并由管理员配置合作方密钥。正式核验使用只读接口及隔离响应，不创建真实执行或交易。
- 外部凭证校验失败、自己的码、他方的码、他方任务、签发后禁用、签发与提交并发、过期授权、响应丢失、重复提交及人工复核需覆盖定向测试。确认同一兑换码只能创建一次未结算的执行任务。
- ID 管理页、ID 客户授权页及 MOYAO 接入页分别验证手机和桌面交互。联调使用合成兑换码、授权资料与执行回执。生产发布及线上验收另按对应授权执行。
